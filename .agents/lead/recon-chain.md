## РАЗРЫВ 1. Долг считается четырьмя выражениями. Расхождение уже есть: 51 400 ₽ против 53 000 ₽

Замерено в одном прогоне, по одной клинике, в один момент времени
(«Демо-клиника для снимков», `d0000000-0000-4000-8000-00000000d001`):

- `GET /api/dashboard` → `billingSummary.totalDueRub` = **51 400 ₽**
- `GET /api/reports/receivables` → `totalDebtRub` = **53 000 ₽**
- `dashboard.patientInsights` → сумма `balanceDueRub` по 14 пациентам = **53 000 ₽**

Причина — четыре независимых формулы:

1. `buildBillingSummary()`, `apps/api/src/sampleData.ts:1346`:
   `totalDueRub = max(0, Σ_клиника(планируемое) − Σ_клиника(оплаченное))` = 118 800 − 67 400 = 51 400.
   Считается ПО ВСЕЙ КЛИНИКЕ одним вычитанием.
2. `receivables()`, `apps/api/src/services/reports/managerReports.ts:841-850`:
   долг считается по КАЖДОМУ пациенту, затем `filter(debtRub >= minDebtRub)` с минимумом 1 ₽,
   то есть отрицательные суммы (переплаты) отбрасываются. 53 000.
3. `patientInsights`, `apps/api/src/sampleData.ts:1885`:
   `balanceDueRub = max(0, planned − paid)` по пациенту, тоже без переплат. 53 000.
4. Клиент, `apps/web/src/useAppLogic.tsx:5171-5174`:
   `totalDueRub = max(0, planned − insuranceCoverageRub − paid)`. **Страховое покрытие
   вычитается только здесь.** Ни один серверный расчёт про ДМС не знает.

Что это значит для клиники. Разница 1 600 ₽ — это переплата двух живых пациентов:
Ковалёв С. И. заплатил 22 000 ₽ за лечение на 21 200 ₽, Орлова М. П. — 5 400 ₽ за 4 600 ₽.
На главном экране их переплата молча зачтена в чужой долг, в отчёте дебиторки они просто
исчезли. Клиника должна двум людям по 800 ₽ и не увидит этого ни на одном экране.

Ещё два будущих расхождения в этих же формулах:
- количество: гидратация округляет его до целого (`domainStateHydration.ts:527`,
  `Math.round(Number(quantity))`), а SQL отчётов берёт `greatest(quantity, 1)`
  (`managerReports.ts:822`). Полторы единицы услуги дадут на экране `×2`, а в отчёте `×1.5`.
  Сегодня дробных количеств в базе 0 — расхождение спит.
- в самой таблице `treatment_items` два итога: `Σ price_rub` = 120 400 ₽,
  а `Σ(unit_price_rub × quantity − discount_rub)` = 118 800 ₽. Колонка `price_rub`
  объявлена `NOT NULL` (`schema.ts:465`) и не читается ни одним денежным расчётом.

## РАЗРЫВ 2. Приём открыть нечем: визит не создаёт ни один маршрут

`POST /api/appointments` пишет только в `appointments` (`db/appointmentsQuery.ts` слова
`visit` не содержит). Вставки в `visits` есть ровно в четырёх местах, и все они вне
рабочего пути:

- `apps/api/src/scripts/migrateStateToDb.ts:181` — разовый перенос состояния;
- `apps/api/src/routes/workspaceProfile.ts:450,499` — демо-пресет мастера первого запуска;
- `apps/api/src/scripts/seedOpsScreenshotDemo.ts:384` — посев для снимков;
- `apps/api/src/migration/loader.ts:1208` — импорт из чужой системы.

А карта приёма всегда работает с `dashboard.activeVisit`, и это «последний ЧЕРНОВИК
клиники, иначе последний визит любого статуса» — `applyActiveVisit`,
`apps/api/src/db/domainStateHydration.ts:828-854`. Клиент нигде не выбирает визит сам:
`useVisitLogic.ts:519,536,543` и `useAppLogic.tsx:2471-2473` берут именно это поле.

Замерено на живой базе:

```
«Демо-клиника для снимков»: дашборд подставит визит d0000000-...-000000000409 статус=signed
  GET  /api/visits/.../draft/autosave -> HTTP 404 {"error":"VisitNotFound",
       "message":"Прием не найден. Обновите рабочий экран и выберите актуальный прием."}
  PUT  автосохранение                 -> HTTP 409 {"reason":"visit_closed",
       "message":"Черновик приема не сохранен: этот прием уже недоступен для изменений."}
«Стоматология, 1 кабинет»: приёмов в базе нет вовсе — карту приёма открывать не на чем.
```

То есть: у клиники с историей карта приёма отвечает 404/409 (`visitsQuery.ts:14,45`
отклоняют любой визит не в статусе `draft`), у клиники без истории — нулевой UUID и
пустой экран. «Обновите рабочий экран и выберите актуальный прием» — обновление ничего
не изменит, потому что выбирать не из чего и создавать нечем.

Отдельно: активный визит ОДИН на клинику. Два кресла — два врача пишут ЭМК в одну карту.

## РАЗРЫВ 3. Касса закрыта для всех пациентов, кроме одного; подсказка предлагает действие, которого нет

`usePatientLogic.ts:140-155`: если `activeVisit.patientId` не равен выбранному пациенту,
`paymentPatientContextReady = false`, и `recordPayment()` (`useAppLogic.tsx:12741-12747`)
выходит с текстом «Сейчас выбран пациент X, но открытый прием идёт у другого пациента.
**Переключите приём**, иначе оплата уйдёт не тому».

Переключателя приёма в продукте нет: ни маршрута, ни функции — поиск по `apps` даёт одно
вхождение слова «Переключите приём», и это сам текст ошибки.

Замерено: живой `activeVisit.patientId` = `d0000000-...-000000000105`, а в клинике 14
пациентов. Значит для 13 из 14 кнопка «Принять оплату» отвечает отказом, и снять его из
интерфейса нельзя — только правкой строки в базе. Барьер сам по себе правильный (деньги
не должны уйти чужому пациенту), но выход из него не построен.

Плюс: в тело оплаты уходит `visitId: realActiveVisitId` (`useAppLogic.tsx:12877`) — тот же
общий визит. Оплата привязывается к визиту, который к этой услуге может не относиться
вовсе, а `payments.visit_id` — единственная связь денег с врачом (см. разрыв 6).

## РАЗРЫВ 5. Отметка выполненного — текст для человека; закрытие приёма закрывает всё подряд

`CompletedServicesChecklist.tsx:79-121` дописывает строку `Выполнено: услуга (зуб 36) — 1 500,50 ₽`
в поле «План» приёма и оттуда же читает состояние галочки. Программного читателя у этой
строки нет ни в API, ни в вебе (замерено: визитов с `Выполнено:` в базе — 0).

Итог «К оплате по отмеченному» (`markedTotalRub`, там же, строка 104) — это ЧЕТВЁРТАЯ
сумма к оплате в системе, посчитанная по отмеченным позициям. Касса её не получает:
`billingSummary.totalDueRub` считается по ВСЕМ не отменённым позициям пациента, а не по
отмеченным (`sampleData.ts:1296,1346`).

Дальше — два разных «закрытия приёма» с разными последствиями для денег:
- подписание ЭМК, `acceptVisitDraftInDb` (`db/visitsQuery.ts:82-105`): ставит
  `visits.status='signed'` и НЕ трогает позиции лечения вовсе;
- подписание дневника, `runDiarySigningCeremony` (`routes/diary.ts:211-221`): переводит в
  `completed` ВСЕ позиции визита одним `UPDATE`, без разбора того, что отметил врач, и
  списывает материалы.

`visit_diaries` в живой базе — 0 строк: второй путь не выполнялся ни разу. При этом все 10
позиций уже `completed` — их так посеяли. Значит статус «выполнено» на живой базе не
подтверждает ничего о фактически сделанной работе.

## РАЗРЫВ 6. Счёт пациенту не существует как данные, но по нему считают портал и BI

`patient_invoices` не пишет НИ ОДИН маршрут (проверено по всему `apps/api/src`). Читают её
двое:
- `routes/portal.ts:612-615` — раздел счетов личного кабинета пациента;
- `scripts/cronAnalyticsWorker.ts:107-120,198-227` — LTV когорт и прибыльность врачей
  (`JOIN patient_invoices i ON i.visit_id = v.id`, `SUM(i.total_amount_rub)`).

В том же ответе портал читает `visit_diaries` (0 строк) и `treatment_plans` (0 строк).
Пациент демо-клиники с 10 подписанными приёмами и лечением на 118 800 ₽ увидит в личном
кабинете пустоту по всем трём разделам, а прибыльность врачей в BI будет нулевой при
выручке 67 400 ₽ в `payments`.

Дополнительно: в живой таблице ДВА итога — `total_amount_rub` и `total_rub` (проверено
`information_schema`). Drizzle-схема объявляет только `total_rub` (`schema.ts:1643`), а
рабочий SQL считает по `total_amount_rub`. Кто бы ни начал писать счёта, он заполнит одну
колонку, а половина читателей возьмёт другую.

Связь денег с врачом держится на том же слабом месте: `doctorPerformance()`
(`managerReports.ts:169-279`) идёт `payments → visits → appointments → doctor_user_id` и сам
пишет в примечании «чтобы выручка попадала врачу, оплату нужно оформлять из визита,
созданного из записи в расписании». Маршрута, создающего такой визит, не существует
(разрыв 2). Сегодня замер даёт «не отнесено к врачу = 0» только потому, что посев
`seedOpsScreenshotDemo.ts` создал визиты с `appointment_id` руками.

## ПРОВЕРЕНО

- Расхождение долга 51 400 ₽ (`/api/dashboard`) против 53 000 ₽ (`/api/reports/receivables`
  и `patientInsights`) на одной клинике в одном прогоне. Переплаты 800 + 800 ₽ у двух
  названных пациентов.
- `GET /api/visits/<живой activeVisit>/draft/autosave` = 404, `PUT` = 409 на подписанном
  визите; у второй клиники визитов 0.
- Количество строк во всех таблицах цепочки (таблица выше), в том числе
  `treatment_plans` 0, `treatment_plan_items_new` 0, `visit_diaries` 0, `cash_ledger` 0.
- `Σ price_rub` 120 400 ₽ против `Σ(unit×qty − discount)` 118 800 ₽ в `treatment_items`.
- `patient_invoices` в живой базе имеет и `total_amount_rub`, и `total_rub`.
- Отсутствие вставок в `visits` и `treatment_items` в боевых маршрутах — поиском по
  `apps/api/src` (`.insert(visits)`, `.insert(treatmentItems)`), с перечислением всех
  найденных мест.
- Отчёты `/api/reports/{receivables,doctors,services,revenue}` отвечают 200 в своём
  процессе; выручка 67 400 ₽ сходится с `SELECT sum(amount_rub) WHERE status='paid'`.

## НЕ ПРОВЕРЕНО

- В браузере ничего не открывалось: тексты отказов кассы и карты приёма разобраны по коду,
  а не увидены на экране.
- `POST /api/patients/:patientId/treatment-plans` в своём процессе не вызывался: вывод «его
  результат не виден деньгам» следует из того, в какие таблицы он пишет и какие таблицы
  читают деньги, а не из наблюдения за одним запросом.
- Оплата (`POST /api/billing/payments`) и списание с семейного счёта не выполнялись:
  замеры по деньгам сделаны на уже существующих строках.
- Поведение при двух одновременно открытых приёмах (два врача, одна карта) выведено из
  `applyActiveVisit`, параллельно не воспроизводилось.
- `cronAnalyticsWorker.runBiAnalyticsAggregation` не запускался: утверждение о нулевой
  прибыльности врачей выведено из пустоты `patient_invoices`, а не из прогона задачи.

1. Разрыв 1 — деньги расходятся сейчас, 1 600 ₽ и невидимые переплаты. Один расчёт долга,

2. Разрыв 2 — без создания визита из записи не работает ни ЭМК, ни привязка денег к врачу.
3. Разрыв 3 — касса физически заперта для большинства пациентов.
4. Разрыв 4 — смета врача не доходит до денег.
5. Разрыв 5 — отметка выполненного не превращается в данные.
6. Разрыв 6 — счёт пациенту и личный кабинет.
