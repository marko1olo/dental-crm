## Чем доказывается достижимость (третий механизм не пишем)

В дереве уже есть зелёный сторож, и он двусторонний, поэтому годится и для монтирования, и
для сноса — `apps/web/src/tests/panelsAreMounted.test.ts` поверх переписи
`apps/web/src/tests/utils/componentReachability.ts`:

```
apps/web> node --import tsx --import ./testCssStub.mjs --test src/tests/panelsAreMounted.test.ts
перепись: 334 файлов, 183 компонентов, 1256 мс
✔ 9 тестов, 0 падений
```

- `appeared` (`:420-434`) краснеет, если компонент стал несмонтированным незаявленно;
- `stale` (`:436-444`) краснеет, если строку из списка убрали, а компонент так и не
  смонтирован, — то есть **вычеркнуть строку и ничего не сделать нельзя**;
- `missingFiles` (`:470-478`) краснеет, если файл удалён, а строка осталась;
- `LEGACY_BACKLOG_CEILING` (`:331`) при сносе обязан опускаться, иначе список перестаёт
  сжиматься.

Поэтому каждая цель ниже доказывается ЭТИМ прогоном плюс своим предметным доказательством
(запрос в базу, снимок экрана, `rg` на отсутствие импортёра). Своего стража не завожу.

**Ловушка удаления, которая в проекте уже срабатывала**: после сноса файла в HEAD оставалась
ссылка на несуществующий модуль. Поэтому у каждого сноса обязательный шаг — `rg` по имени
компонента и по имени файла даёт ноль совпадений вне `panelsAreMounted.test.ts`, и только
после этого `npm run typecheck` (гейт общий, один писатель за раз — `.agents/AGENTS.md` §7a).
