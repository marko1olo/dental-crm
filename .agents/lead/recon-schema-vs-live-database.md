## 2. Чем измерено

### 2.1 Прямой запрос к каталогу

```bash
PGPASSWORD=dental ./.postgres/bin/psql.exe -h 127.0.0.1 -p 5432 -U dental -d dental_crm -c "..."
```

Каталог читается через `pg_attribute` + `format_type()`, а НЕ через `information_schema.columns`, и это
не вкусовщина: `information_schema` отдаёт `data_type = 'USER-DEFINED'` для любого перечисления и
`'ARRAY'` для любого массива, то есть теряет ровно то имя типа, которое надо сверить. Сверять
«USER-DEFINED» с «treatment_plan_status» нельзя. `format_type()` возвращает `treatment_plan_status`,
`numeric(12,2)`, `text[]` — то же, что печатает `getSQLType()` у drizzle.

### 2.2 Замок как инструмент разведки

`apps/api/src/tests/schemaMatchesLiveDatabase.test.ts` (создан этой волной) сверяет **метаданные,
которые построил сам drizzle** (`getTableConfig()`), с каталогом PostgreSQL. Разбором текста `schema.ts`
это делать нельзя: существующий `scripts/check-schema-type-drift.mjs` читает объявления регуляркой по
строке и потому не видит ни `.notNull()`, перенесённого на следующую строку, ни `.default()`, ни колонку,
собранную вспомогательной функцией.

Чем замок отличается от уже имеющегося `check-schema-type-drift.mjs`: тот сверяет ТОЛЬКО тип и падает
ТОЛЬКО на денежных именах — остальное печатает и возвращает ноль. Наличие колонки, обязательность,
умолчание и набор значений перечисления он не сверяет вовсе, то есть **четыре из пяти названных
расхождений проходят через него зелёными**. Скрипт не заменён: у него своя область (денежный дрейф как
гейт `npm run lint`).

обход приведениями к тексту в `routes/imaging_planning.ts`. Это важно не для протокола, а для решения:
переход на настоящий `jsonb` больше не требует переписывания испорченных строк, и аргумент «данные

## 5. `treatment_plans.status`: отказывает ли PostgreSQL уже сейчас

**Ответ: НЕТ, сегодня не отказывает. Но регистр уже стоит клинике целого отчёта.**

### 5.1 Перепись писателей — все до одного

```
apps/api/src/routes/odontogram.ts:564   db.insert(treatmentPlans)   — боевой, единственный
apps/api/src/routes/odontogram.ts:542   db.update(treatmentPlans)   — боевой, единственный
apps/api/src/services/tests/recallScheduler.test.ts:42,73,109,143,171,199 — тесты
```

Ни в `apps/api/src`, ни в миграциях больше нет ни одного `insert`/`update` по `treatment_plans` — ни
через drizzle, ни сырым SQL (`rg 'into treatment_plans'` — ноль).

### 5.2 Почему отказа нет

Боевая вставка (`odontogram.ts:565-574`) передаёт `organizationId, patientId, name, totalPrice,
patientSignature, isSynced, version, updatedAt` — и **не передаёт `status` вовсе**. Для колонки со
статическим `.default(...)`, значение которой не передано, drizzle подставляет в SQL не значение из
`schema.ts`, а ключевое слово `default` — решение отдаётся базе. База применяет своё умолчание `'Draft'`.
Строчный `"draft"` из объявления в запрос не попадает никогда. Обновление статус тоже не трогает.

Тест `recallScheduler.test.ts:47` передаёт `status: "Active"` — с большой буквы. Его автор, судя по
значению, уже выяснил настоящий набор эмпирически; в объявлении это знание не отражено.

### 5.3 Что регистр стоит клинике УЖЕ СЕЙЧАС

`apps/api/src/scripts/cronAnalyticsWorker.ts:173-200` — воронка планов лечения в суточном срезе
BI-аналитики:

```ts
const funnelMap: Record<string, number> = { draft: 0, proposed: 0, approved: 0, active: 0, completed: 0 };
for (const p of planCounts) {
    if (p.status in funnelMap) funnelMap[p.status] = p.count;   // 'Draft' in funnelMap === false
}
```

Ключи строчные, база отдаёт `Draft`/`Active`/`Approved`/`Completed`/`Rejected`. Условие `p.status in
funnelMap` не выполняется НИКОГДА, ни для одного статуса. Воронка «Draft / Proposed / Approved / Active /
Completed» в отчёте руководителю показывает нули при любом числе планов в базе. Отказа нет, есть тихий
ноль — то есть худший из двух вариантов: руководитель видит цифру и ей верит.

Дополнительно: `funnelMap` знает `proposed`, которого в перечислении базы нет вовсе, и не знает
`Rejected`, который в нём есть. Это второй, независимый признак того, что словарь статусов в коде и в
базе никогда не сверялись.

### 5.4 Чем это заряжено на будущее

Пока никто не передаёт статус — тихо. Первое же место, которое передаст его строчной строкой (или
сравнит: `where(eq(treatmentPlans.status, "draft"))`), получит от PostgreSQL
`invalid input value for enum treatment_plan_status: "draft"` в рантайме, потому что параметр приводится
к типу колонки. Объявление `text` этого не запрещает — компилятор пропустит любую строку. Перевод
объявления на `pgEnum` делает такую ошибку невозможной на этапе компиляции.

`cronAnalyticsWorker.ts` — не моя область (правка воронки требует решения, какие ветви показывать
руководителю); расхождение внесено в отчёт ведущему как отдельный долг.

## 6. `jsonb` против `text`: решение и его основание

**Решение: объявление приводится к `text`. Миграция не нужна.**

Доводы в пользу `jsonb` есть: он валидирует форму на входе и позволяет запрашивать разметку по частям.
Оба довода на этом участке не работают, и вот почему — фактом, а не вкусом.

1. **Проволочный контракт маршрута — СТРОКА, и он уже закреплён с двух сторон.**
   `routes/imaging_planning.ts:68-70` принимает `splinePointsJson: z.string().optional()`;
   `apps/web/src/components/dicom/ctPlanningPersistence.ts:215-217` объявляет у ответа
   `splinePointsJson: string` и делает `JSON.stringify` на отправке и `JSON.parse` на приёме. Уже
   написанный тест маршрута `apps/api/src/tests/routes/ctPlanningMarkupPersists.test.ts:205-207`
   утверждает `assert.equal(typeof planning.splinePointsJson, "string")`.
   Настоящий `jsonb` заставит drizzle отдавать РАЗОБРАННЫЙ массив вместо строки: этот тест краснеет,
   клиент ломается. Клиент лежит в `apps/web/**` — вне моей области.

2. **`jsonb` не даст обещанной проверки формы, пока маршрут передаёт строку.** Класс `jsonb` у drizzle
   на записи делает `JSON.stringify` от того, что ему дали. Дают строку — в колонку уходит строка в
   кавычках, то есть возвращается ровно та двойная кодировка, из-за которой этот дефект и начался.
   Чтобы `jsonb` валидировал, маршрут обязан разбирать тело в объект и передавать объект: это правка
   контракта маршрута И клиента, а не правка типа колонки.

3. **Договор проекта на такие колонки — `text`.** В `schema.ts` девятнадцать колонок с суффиксом
   `_json`, хранящих текст, объявлены `text` (`treatment_scenarios.phases_json`,
   `clinical_rules.trigger_service_ids_json`, `dente_telegram_bot_configs.enabled_features_json`
   и далее). `patient_ct_plannings` — исключение, а не образец.

4. **Цена: ноль.** `text` в объявлении совпадает с базой дословно, миграция не нужна, данные не
   трогаются. Настоящий `jsonb` стоил бы миграции с `ALTER COLUMN ... TYPE jsonb USING ...::jsonb` плюс
   правки маршрута плюс правки клиента плюс переписывания уже зелёного теста.

**Что станет с обходом в `routes/imaging_planning.ts`.** После правки объявления приведения `::text`
на чтении и записи становятся НЕНУЖНЫМИ: колонка `text`, drizzle отдаёт и принимает строку без
преобразований. Они при этом остаются безвредными. Обход снимается вместе с той частью шапки файла,
которая объясняет расхождение: шапка утверждает «`db/schema.ts:1901-1903` объявляет `jsonb`», и после
правки это утверждение становится ЛОЖЬЮ. Оставить в файле объяснение обхода, которого больше нет, —
ровно тот класс устаревающей молча прозы, за который в этом дереве уже платили (`NO_CONTRACT_PAIR`:
из пяти названных номеров строк не совпал ни один).

### 7.3 Правды нет ни там, ни там (1)

**`treatment_plans.name`.** Объявление: `.notNull().default("План лечения")`. База: `NOT NULL`,
умолчания НЕТ.

Это единственное расхождение в области, где неправы оба, и оно заряжено на отказ. drizzle для колонки со
статическим умолчанием, значение которой не передано, пишет в SQL `default`, а не значение из
`schema.ts`. У колонки в базе умолчания нет, `NOT NULL` есть — значит вставка без `name` даёт
`null value in column "name" violates not-null constraint`. Объявление обещает, что поле необязательно;
база это обещание отвергает. Сегодня не рвётся только потому, что оба существующих писателя `name`
передают.

**Что должно быть: `.notNull()` без умолчания.** Не «добавить умолчание в базу»: план лечения, тихо
сохранённый под общим именем «План лечения», — это документ, который врач не найдёт в списке из десяти
таких же, и подпись пациента на нём будет стоять под безымянной сметой. Правильный ответ — требовать имя,
и требовать на этапе компиляции. Снятие `.default(...)` делает `name` обязательным в типе вставки, то
есть превращает отказ в рантайме в ошибку компилятора. Оба существующих писателя это уже переживут без
правки.

### 7.4 Не расхождение, но долг рядом — ведущему

`treatment_plan_items_new.organization_id` допускает `NULL` И в базе, И в объявлении: расхождения нет,
поэтому замок молчит и правка вне мандата. Но это позиции сметы без принадлежности клинике —
та же дыра изоляции, что закрывали у `family_groups`. Таблица сейчас пуста (0 строк), то есть закрыть
дыру стоит одного `SET NOT NULL` плюс `.notNull()` в объявлении — и это самый дешёвый момент за всю
жизнь таблицы. Решение за ведущим.

## 9. Что требует потери данных

**Ни одно расхождение из 292 не требует ни `DROP`, ни `ALTER` с потерей.** Все пять миграционных ALTER
области — `SET NOT NULL` на таблицах, где NULL-строк ноль (замерено, раздел 7.2), и каждый откатывается
обратным `DROP NOT NULL` без следа.

Единственная группа, где сведение В ДРУГУЮ СТОРОНУ стоило бы данных, — 41 расхождение по типу вне
области, если решать их изменением типа В БАЗЕ: `character varying(50)` → `text` безопасно, а обратно
`text` → `varchar(50)` обрежет значения длиннее предела. Поэтому по всем 41 правильное направление —
править объявление, и ни одна из них не внесена в правку этой волны только из-за границ участка.

## 10. Замок: устройство и почему он не выродится

`apps/api/src/tests/schemaMatchesLiveDatabase.test.ts`, семь сверок плюс три самопроверки.

* **Живая база — пропуск с причиной, а не молчаливый зелёный.** Без `DATABASE_URL` или при недоступном
  сервере каждая сверка помечает себя `skip` с текстом «НЕ СВЕРЕНО с живой базой: …», называя адрес
  (без пароля) и причину отказа соединения. `SCHEMA_LOCK_REQUIRE_DATABASE=1` превращает пропуск в отказ.
* **Подключение своим клиентом, а не через `db/client.ts`:** тот модуль бросает исключение на этапе
  загрузки при незаданном `DATABASE_URL`, и файл теста не загрузился бы вовсе — вместо честного пропуска
  прогон получил бы падение загрузки без объяснения.
* **Три самопроверки от вырождения.** Перепись модулей `db/` требует, чтобы ни один файл с `pgTable` не
  выпал из списка импортов (так уже терялся `communication_campaign_status` из
  `db/communicationsSchema.ts`). Перепись объявлений требует не меньше 120 таблиц и 1200 колонок с
  непустыми типами. Сравнение типов проверяется на образцах в обе стороны: синонимы одного типа
  (`varchar(50)` и `character varying(50)`, `numeric(12, 2)` и `numeric(12,2)`) обязаны совпадать, а
  настоящие расхождения (`jsonb`/`text`, `text`/перечисление, разная точность `numeric`, время с поясом
  и без, массив против скаляра) — обязаны краснеть.
* **Реестр `KNOWN_DIVERGENCES` работает в обе стороны.** Новое расхождение валит прогон с именем
  колонки. Исчезнувшее — тоже, с требованием убрать запись тем же коммитом. Так реестр не превращается
  в место, куда сметают новые расхождения, и не начинает врать.

## 11. `patient_invoices`: корневая причина обнуления выручки — у таблицы НЕТ писателя

Дополнение от сверки 2026-08-04 (статическая, без живой базы). В разделе 4 и в
`schema.ts:1685-1704` дефект описан как «аналитика читает `total_amount_rub`, а drizzle пишет
`total_rub`». Сверка по всему дереву уточняет картину жёстче:

**В `patient_invoices` не пишет НИКТО — ни drizzle, ни сырой SQL.**

*   `patientInvoices` импортируется ровно в двух местах, и оба читают:
    `routes/portal.ts:639` (список счетов в личном кабинете) и
    `scripts/cronAnalyticsWorker.ts:5` (выручка).
*   Ни одного `db.insert(patientInvoices)`, `insertInto(patientInvoices)`, `into patient_invoices`
    или `INSERT INTO patient_invoices` в `apps/api/src`, `scripts/` и миграциях нет.
*   Счета реально заводятся как `generated_documents` с `kind = 'payment_invoice'`
    (`schema.ts:217`); самоподписанный контур проверяет именно `generated_documents.total_amount_rub`
    (`tests/chains/moneyChainProof.ts`, `tests/routes/invoiceKeepsItsAmount.test.ts`).

**Что это значит для отчётов.** `cronAnalyticsWorker.ts` считает выручку когорт LTV (строка ~155) и
выручку по врачам (строка ~250) сырым SQL по `patient_invoices.total_amount_rub WHERE status='paid'`.
Поскольку таблица никогда не наполняется, **оба отчёта всегда показывают ноль**, независимо от того,
какую колонку читать. Это не «аналитика читает не ту колонку» — это «таблица-сирота без источника».

**Почему не «простых решений».** Два честных направления, и каждое требует решения ведущего:

1.  *Переключить аналитику на `generated_documents`.* Это источник правды для созданных счетов.
    Нужно: переписать оба запроса (`total_amount_rub` → `generated_documents`, фильтр по `kind =
    'payment_invoice'` и `status = 'issued'`/оплаченным), затем живая сверка сумм по двум таблицам.
2.  *Наполнять `patient_invoices` при создании счёта.* Это восстанавливает задуманную денормализацию
    (состав счёта `items_json`, `patient_amount_rub`, `insurance_amount_rub`). Нужно: писатель на пути
    создания `generated_documents` kind=`payment_invoice`, миграция на недостающие колонки объявления
    (`items_json`, `patient_amount_rub`, `insurance_amount_rub`, `updated_at`) и сведение `total_rub` /
    `total_amount_rub` в один столбец.

Любое из двух — отдельный пакет с живой проверкой сумм до и после; обнуление выручки у руководителя —
прямая цена бездействия. Замок на это место уже стоит: `KNOWN_DIVERGENCES` держит
`patient_invoices.total_rub` (nullable), `patient_invoices.status` (тип) и `items_json`/
`patient_amount_rub`/`insurance_amount_rub`/`updated_at` (undeclared).

## 12. `doctor_commissions`: двойная колонка процента НЕ дефект денег — расчёт читает `commission_pct`

Дополнение от сверки 2026-08-04 (статическая, без живой базы). В отличие от `patient_invoices`
(раздел 11), здесь деньги НЕ теряются, и причин для спешки нет — но это ровно тот случай, где
«двойная колонка» соблазняет на «простое решение», которое сломает выплаты.

**Факт колонок.** Миграция `0000` создала `commission_pct real DEFAULT 30 NOT NULL` — изначальная
колонка. Миграция `0118` дописала дубль `commission_percent numeric(5,2) DEFAULT '25'`. Миграция
`0121` перевела `commission_pct` в `numeric(5,2)` DEFAULT '25'. Обе колонки объявлены в модели.

**Как код этим пользуется — и почему это правильно:**
*   Писатель `setDoctorCommissionRateInDb` (`db/settingsQuery.ts:588-615`) заполняет ОБЕ колонки
    (`commissionPct` и `commissionPercent`) синхронно — двойная колонка не расходится на записи.
*   Читатель выплат (`services/finance/doctorPayouts.ts`) везде берёт `commission_pct`. Комментарий
    в начале файла (`:22-25`) объясняет, почему `commission_percent` — ловушка: у неё живой
    DEFAULT '25', и старые строки, записанные до дубля, несут в ней 25 при настоящей ставке 30.
    Прочитать её — заплатить врачу 25 % вместо 30 %.
*   Тест `doctorPayouts.test.ts` — 13/13 зелёных, включая копейки и случай `commissionPct: null`.

**Вердикт.** Двойная колонка — наследие, а не активный дефект денег. Расчёт уже читает правильную
колонку, запись держит пару синхронной. Убирать `commission_percent` — отдельное решение ведущего
(тогда и `diary.ts`, и `settingsQuery.ts` теряют зеркальную запись). `specialty`/`service_category`
(в базе перечисления, в модели text) уже обрабатываются явной передачей значений и описаны как
продуктовый долг в `settingsQuery.ts`: раздельных ставок по категориям услуг в продукте нет.

## 13. `patient_duplicate_merge_queues`: объявлен мёртвым — реестр держит его как улику, не как баг

Дополнение от сверки 2026-08-04 (статическая, без живой базы). Это единственная телескопическая
таблица, чьи записи в `KNOWN_DIVERGENCES` выглядят как «живой» дрейф, но на деле это застывшая улика
отказа от таблицы.

**Факт миграций.** Миграция `0094` создала очередь. Миграция `0128` завела `patient_duplicate_decisions`
и в комментарии явно объявляет `patient_duplicate_merge_queues` мёртвой: «в живой базе одновременно
есть primary_patient_name / duplicate_patient_name / match_confidence_percent / merge_status (их ждёт
виджет) и source_patient_id / target_patient_id / match_score / status (их объявляет ORM)». Виджет читает
первое поколение, код пишет второе, маршрута между ними нет вовсе — проверено запросом, 404.

**Отсюда каждая строка реестра — след того самого разрыва, а не новый дефект:**
*   `nullableInDatabase`: `source_patient_id` и `target_patient_id` (в модели NOT NULL, в базе nullable),
    `status` (есть в базе, в модели не объявлен).
*   `undeclaredInModel`: `duplicate_patient_name`, `match_confidence_percent`, `merge_status`,
    `primary_patient_name` (колонки виджета, которых в модели нет).

**Вердикт.** Лечить эти записи — значит чинить мёртвую таблицу, что ровно то «простое решение», от
которого предостерегает `0128`. Настоящий источник истины по дублям — `patient_duplicate_decisions`
(человеческое решение, не очередь). Статическая сверка не даёт права ни на DROP, ни на «переезд»
колонок без живой базы. Действия по мёртвой таблице (оставить, DROP в отдельной миграции, убрать
записи реестра) — решение ведущего, обязано пройти с поднятой базой и `SCHEMA_LOCK_REQUIRE_DATABASE=1`.
