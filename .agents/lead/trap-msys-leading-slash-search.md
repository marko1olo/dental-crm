# Ловушки измерения на этой машине разработки

Их две, и обе устроены одинаково: инструмент не жалуется, не возвращает кода ошибки и выдаёт
правдоподобный ответ, который просто НЕ ОТНОСИТСЯ к тому, что спрашивали. Такой ответ опаснее
падения: падение видно, а тихий неверный ответ становится доказательством в чужом отчёте.

## Ловушка 2: `TZ=...` перед командой не доезжает до процесса

Проверено замером 2026-07-29, нашёл инженер, которому я сам предписал неверный способ:

```
$ TZ='Asia/Kamchatka' node -e "console.log(process.env.TZ, Intl.DateTimeFormat().resolvedOptions().timeZone)"
undefined Europe/Samara          # пояс ХОСТА, переменная не дошла вовсе

$ node -e "process.env.TZ='Asia/Kamchatka'; console.log(Intl.DateTimeFormat().resolvedOptions().timeZone)"
Asia/Kamchatka                   # присваивание ВНУТРИ процесса работает
```

MSYS вырезает `TZ` из окружения родных процессов Windows. `export TZ=`, `env TZ=` — то же самое.

**Чем это опасно именно здесь.** В проекте целое направление про часовые пояса: «дата считается в
поясе сессии вместо пояса клиники». Естественный замер — «прогони то же самое в другом поясе и
покажи разницу». Выполненный через `TZ=`, он возвращает ОДИН И ТОТ ЖЕ ответ для всех поясов, из
чего читается «разницы нет, дефекта нет». То есть ловушка не просто мешает — она выдаёт
доказательство ОТСУТСТВИЯ настоящего дефекта. Один такой замер был предписан в задании ведущего и
был бы принят, если бы исполнитель не перепроверил.

**Как мерить пояс правильно:** присваивать `process.env.TZ` внутри процесса до первого обращения к
датам, либо вообще не трогать пояс процесса и передавать зону явным аргументом
(`Intl.DateTimeFormat("en-CA", { timeZone })`, `AT TIME ZONE 'zone'`). Второй способ лучше: он
измеряет то, что делает боевой код, а не настройку процесса.

## Ловушка 1: поиск по шаблону с ведущим слэшем возвращает ноль молча

Дата: 2026-07-29. Проверено замером, воспроизводится одной командой.

## Факт

Git Bash (MSYS2) на машине разработки выполняет преобразование аргументов-путей: **любой аргумент
команды, начинающийся с `/`, переписывается в путь Windows ДО того, как его увидит программа.**

```
$ node -e "console.log(process.argv.slice(1))" "/api/auth/register"
argv: [ 'C:/Program Files/Git/api/auth/register' ]
```

Следствие для поиска по коду:

```
$ rg "/api/auth/register" apps/api/src      # ноль строк
$ rg -F "/api/auth/register" apps/api/src   # ноль строк
$ rg "api/auth/register" apps/api/src       # найдено: routes/auth.ts:467
```

Маршрут всё это время стоял в `apps/api/src/routes/auth.ts:467`. Поиск не жалуется, не предупреждает
и не возвращает кода ошибки — он возвращает пустой вывод, который читается как «такого нет».

## Почему это дорого

Пустой результат поиска в этом дереве регулярно служит доказательством в приговорах: «маршрута нет»,
«ноль вызывающих», «модуль мёртвый», «адрес не обслуживается». Каждый такой приговор, полученный
шаблоном с ведущим слэшем, **недействителен**.

С высокой вероятностью именно это — настоящая причина ложной тревоги «сервер не обслуживает 19
адресов», из которых при ручной проверке обслуживались 14. Тревога стоила часа набора в красном и
одного отозванного заголовка.

## Обходы, оба проверены

```
MSYS2_ARG_CONV_EXCL='*' rg -F "/api/auth/register" apps/api/src   # находит
rg "api/auth/register" apps/api/src                               # находит
```

Второй способ проще и достаточен почти всегда: ведущий слэш в шаблоне поиска по коду не нужен, а
адрес `api/auth/register` без него столь же однозначен.

## ПОПРАВКА: ловушка ШИРЕ, чем ведущий слэш в начале шаблона

Первая редакция этого разбора утверждала, что страдают только шаблоны, начинающиеся с `/`. Это
неверно, и нашёл это не автор разбора, а инженер приёмки храповика адресов — он наступил на ловушку
лично, но пустой вывод не принял и перемерил.

Переписывается и **часть аргумента внутри**, если она выглядит как путь:

```
$ rg 'app\.delete\("/api'          # ноль строк
# в программу уходит:  app\.delete\("C:/Program Files/Git/api
```

То есть правило «не начинать шаблон со слэша» недостаточно. Опасен любой шаблон, где после кавычки
или скобки идёт `/`, похожий на абсолютный путь Unix.

Надёжных способов два, и оба стоит помнить:

1. `MSYS2_ARG_CONV_EXCL='*'` перед командой — отключает преобразование целиком, работает для любого
   шаблона.
2. Не писать в шаблоне `"/` вовсе: `rg 'app\.delete\(.\.?api'` либо просто `rg 'api/clinical/rules'`.

## Правило

- Шаблон поиска по коду НЕ начинать с `/`, и НЕ писать `"/` внутри. Когда сомневаешься —
  `MSYS2_ARG_CONV_EXCL='*'`.
- Утверждение «маршрута нет» доказывает **ответ 404 от `app.inject`** на поднятом в своём процессе
  Fastify, а не пустой вывод поиска. Пустой вывод — повод перемерить, а не приговор.
- Это касается не только адресов: шаблоны `/src/`, `/components/`, `/api/`, любой путь с ведущим
  слэшем — та же ловушка.

## Что ловушкой НЕ затронуто

Проверено: ни один закоммиченный тест и ни один скрипт в `scripts/` не шеллит внешний поиск с
шаблоном, начинающимся со слэша. Храповик адресов `apps/api/src/tests/webCallsExistingRoutes.test.ts`
разбирает файлы средствами Node, а не внешней командой. То есть ловушка живёт только в руках
человека и агента, а не в наборе проверок.
