## 1. Как именно получается минус. Формула по фактам

Считает `computeDoctorPayout` — `apps/api/src/services/finance/doctorPayouts.ts:256-297`.

```
начислено = касса_врача × commission_pct / 100                       (строка 264)
удержано  = себестоимость_материалов × material_cost_deduction_pct / 100  (строка 290)
к_выплате = начислено − удержано                                     (строка 295)
```

Округление до копейки — `percentOfMoney` (строка 220) и `roundMoney` (строка 215), `Decimal`,
половина вверх. Знак не трогается нигде: `roundMoney` отдаёт то, что получилось.

Поля, из которых берутся числа:

| Величина в формуле | Откуда берётся | Файл:строка |
|---|---|---|
| касса врача | `sum(payments.amount_rub)` по `status='paid'`, `paid_at` в периоде, цепочка `payments.visit_id → visits.appointment_id → appointments.doctor_user_id` | `doctorPayouts.ts:421-446` |
| себестоимость материалов | `sum(unit_cost_rub × abs(quantity_changed))` по `inventory_transactions`, только `transaction_type='auto_deduct'`, только по визитам, чья оплата попала в период | `doctorPayouts.ts:448-485` |
| ставка | `doctor_commissions.commission_pct` (не `commission_percent`), соединение по `user_id`, самая свежая активная строка | `doctorPayouts.ts:494-520,542` |
| процент удержания | `doctor_commissions.material_cost_deduction_pct` | `doctorPayouts.ts:499,543` |

### Условие отрицательности — алгебра, а не наблюдение

```
к_выплате < 0  ⟺  касса × c < себестоимость × d      (c = ставка %, d = удержание %)
               ⟺  себестоимость / касса  >  c / d     (при d > 0)
```

Точка безубыточности по себестоимости: `касса × c / d`.
Доля материалов в кассе, до которой выплата остаётся положительной: `c / d`.

| Ставка `c` | Удержание `d` | Минус начинается, когда материалы превысили |
|---|---|---|
| 10 % | 100 % | **10 %** кассы врача |
| 25 % | 100 % | 25 % кассы |
| 30 % | 100 % | **30 %** кассы |
| 30 % | 50 % | 60 % кассы |
| любая | 0 % | никогда |

### Разбор конкретных чисел из доказательного прогона

`doctorPayoutsProof.ts:556-559` — врач с дорогими материалами:

```
касса          1 000 ₽   (одна оплата, doctorPayoutsProof.ts:385-391)
ставка         10 %      (doctorPayoutsProof.ts:502-510)
начислено      100 ₽     = 1 000 × 10 %
себестоимость  500 ₽     = 250,00 × 2 шт (doctorPayoutsProof.ts:483-491)
удержание      100 %
удержано       500 ₽
к выплате      −400 ₽
```

Безубыточность здесь — 100 ₽ материалов (10 % кассы). Фактически израсходовано 500 ₽, это **50 %
кассы врача** — впятеро выше порога. Минус получился не из-за копеечной погрешности и не из-за
редкого случая: соотношение промахнулось в пять раз.

Для сравнения, врач со ставкой 30 % в том же прогоне (`doctorPayoutsProof.ts:538-547`): касса
1 500,55 ₽, материалы 246,90 ₽ — это 16,45 % кассы, порог 30 %, поэтому выплата положительная
(+203,27 ₽). Разница между этими двумя строками — **не в работе врачей, а в ставке**: 10 % против 30 %.

Итог по клинике `payoutRub: -196,73` (`doctorPayoutsProof.ts:565`) — это `203,27 + (−400)`, то есть
разность двух встречных величин, см. раздел 4.

## 2. Что человек видит сейчас. Замеры по коду и оформлению

Наблюдение ведущего «красное отрицательное число без объяснения» подтверждается частично, и по
замерам оно **хуже**, чем сформулировано: объяснение у строки формально есть, но оно без чисел и без
действия, а оформление ячейки прямо говорит «ошибка».

**2.1. Ячейка «К выплате» помечена крестом.** `DoctorPayoutDashboard.tsx:435-438`:
отрицательная выплата рендерится как `<span className="ops-state ops-state--bad">{money(...)}</span>`.
В `apps/web/src/styles/dente-operations.css:365-370` этот класс — красная плашка, и строка 370:

```css
.ops-state--bad::before { content: "✕"; }
```

То есть владелец видит в денежной колонке **`✕ −400 ₽` красной плашкой**. Второе и единственное
другое употребление этого класса во всём вебе — `components/schedule/DayConfirmationsPanel.tsx:293`,
где им помечено «телефона нет». В этой системе оформления `ops-state--bad` означает «данных нет /
сделать нельзя», а `ops-state--ok` ставит «✓», `ops-state--warn` — «•» (css:352-363). Мы поставили
знак ошибки на достоверную сумму денег. Именно так врач и прочитает: «программа не посчитала» или
«с меня требуют доплату». Экранный диктор произнесёт «✕ минус 400 рублей».

**2.2. Объяснение есть, но без чисел и без действия.** Сервер выдаёт текст
`doctorPayouts.ts:360-365`:

> «Выплата отрицательная: материалы дороже начисленного процента. Это долг врача клинике, а не ноль
> — обнулять его нельзя.»

Три дефекта этого текста:
- **Ни одного числа.** Не сказано, сколько начислено и сколько удержано. Требование ведущего
  («удержано за материалы 500 ₽, начислено 100 ₽») не выполнено.
- **«Обнулять его нельзя» — фраза для программиста, не для владельца.** Владелец ничего не обнуляет;
  он не понимает, к кому обращено это предложение. Действия в тексте нет вовсе.
- **Не сказано, что делать.** Ни проверить ставку, ни проверить списание, ни поговорить с врачом.

**2.3. Объяснение оторвано от числа и утоплено в однообразии.**
Текст строки печатается не в ячейке, а списком под таблицей — `DoctorPayoutDashboard.tsx:455-461`,
по одному пункту на каждого врача, в порядке строк, связь только по фамилии. При восьми врачах
владелец должен глазами найти нужный пункт. Хуже: у каждой посчитанной строки текст начинается
одинаковой фразой `doctorPayouts.ts:341` — «Начислено процентом от кассы, затем удержана доля
себестоимости материалов». Восемь одинаковых первых предложений — и читать список перестают ровно
до того места, где сказано про минус.

**2.4. У итога по клинике объяснения нет вообще.** `DoctorPayoutDashboard.tsx:474-492`: при
`totals.payoutRub < 0` плитке добавляется класс `ops-metric--danger` (css:227-229 — красный цвет
значения) и печатается «−196,73 ₽» под подписью «к выплате всего». Ни одного пояснительного абзаца,
привязанного к отрицательному итогу, в файле нет — я искал по всему файлу: условие
`totals.payoutRub < 0` встречается один раз, в строке 477, и только для класса. Здесь наблюдение
ведущего верно буквально: **крупное красное отрицательное число без единого слова**.

Тот же красный цвет плитки используется и когда не посчитан ни один врач (`nothingComputed`, строка
477) — там показывается «—». Один и тот же визуальный сигнал обслуживает два разных утверждения:
«расчёта нет» и «врачи должны клинике». Их нельзя оформлять одинаково.

## 3. Минус — признак ошибки НАСТРОЙКИ, и это доказуемо в этом репозитории

Да. Причём не по общим рассуждениям о доле материалов в стоматологии, а по двум писателям ставки,
которые расходятся между собой.

**3.1. `material_cost_deduction_pct = 100` никто в клинике не выбирал — это константа в коде.**
`apps/api/src/routes/diary.ts:367-378`: при подписании приёма, если у врача ещё нет строки ставки,
система **сама создаёт** её со значениями

```ts
commissionPct: "30.00",
materialCostDeductionPct: "100.00",
```

Ни одного вопроса клинике не задаётся. Порог безубыточности для такой строки — 30 % кассы.

**3.2. Второй писатель ставит другое удержание — ноль.**
`apps/api/src/routes/workspaceProfile.ts:779-786` (мастер первичной настройки, POST
`/api/workspace/onboarding/complete`) пишет только `commissionPct` и **не пишет
`material_cost_deduction_pct` вовсе** → срабатывает `DEFAULT '0'` из
`apps/api/src/db/schema.ts:1691`. У такого врача выплата отрицательной не бывает никогда.

Итог: в одной клинике врач, заведённый мастером настройки, удерживает **0 %** себестоимости, а врач,
которому строку ставки создало подписание приёма, — **100 %**. Одинаковая работа, одинаковые
материалы, разная зарплата, и разница обусловлена тем, каким кодом создалась строка. Это не политика
клиники. Это расхождение двух писателей.

**3.3. Изменить ни ставку, ни удержание из интерфейса нельзя.** Проверено поиском по всему дереву:
- маршрута записи `doctor_commissions` не существует — ни `POST`, ни `PUT`, ни `PATCH`
  (`rg "app\.(post|put|patch)\(.*commission"` — пусто); писателей ровно два, оба перечислены выше;
- в вебе `commissionPct` встречается только в `DoctorPayoutDashboard.tsx` (чтение) и в комментарии
  `components/reports/ManagerReportsPanel.tsx:383`;
- `materialCostDeductionPct` в вебе не встречается вообще, кроме типа и чтения в этом же экране
  (`DoctorPayoutDashboard.tsx:77,425`);
- единственное поле процента в интерфейсе — шаг первичной настройки
  `components/workspace/onboarding/steps/Step5Staff.tsx:260-277`, и тот же обработчик каждый раз
  **создаёт нового сотрудника** (`workspaceProfile.ts:766-777`), то есть повторный проход мастера не
  меняет ставку, а плодит дубли персонала.

**Отсюда прямое следствие для текста экрана: писать «измените ставку в настройках» нельзя — такого
экрана нет.** Текст, отправляющий владельца в ненайденное место, хуже молчания: клиника решит, что
не разобралась в интерфейсе.

**3.4. Что владелец действительно может исправить сегодня** (проверено по маршрутам):
- цену складской позиции `inventory_items.unit_cost_rub` — `apps/api/src/routes/inventory.ts:136`
  (создание) и `:309` (изменение). Внимание: оба места делают `String(Math.max(0, unitCostRub))` при
  умолчании `0`, то есть позиция без цены молча получает нулевую себестоимость;
- правило списания «сколько материала на услугу» —
  `apps/api/src/routes/inventory.ts:~430-505` (создание/обновление, `quantity_to_deduct`,
  `Math.max(1, ...)`) и удаление ниже. Завышенное количество в правиле или завышенная цена позиции
  дают ровно тот же минус, что и неверная ставка, — и это чинится клиникой самостоятельно.

## 4. Итог по клинике: непонятен, и в нём складываются несопоставимые вещи

`doctorPayouts.ts:702-763`. Разбор по составу.

**4.1. Отрицательный итог — это сальдо, а не сумма к выплате.** −196,73 ₽ = 203,27 ₽ (нужно
выплатить первому врачу) + (−400 ₽) (второй должен клинике). Плитка подписана «к выплате всего»
(`DoctorPayoutDashboard.tsx:489`). Это неверное утверждение: **−196,73 ₽ выплатить невозможно**, а
зачесть долг одного врача из зарплаты другого — нельзя ни по договору, ни по бухгалтерии. Клиника
должна увидеть два числа: сколько отдать (203,27 ₽) и сколько ей должны (400 ₽). Сейчас оба скрыты
внутри одного, и восстановить их можно только сложением строк таблицы вручную.

**4.2. Знаменатель у соседних плиток разный.** Рядом стоят (строки 493-517):
`accruedRub` = 550,17 ₽ («начислено процентом»), `withheldMaterialRub` = 746,90 ₽ («удержано за
материалы») и `revenueRub` = 3 500,55 ₽ («касса клиники за месяц»). Первые две складываются **только
по врачам с пригодной ставкой** (`doctorPayouts.ts:711-715`), третья — это касса **всей клиники**,
включая 300 ₽ без врача и 700 ₽ врача без ставки (`doctorPayoutsProof.ts:562-564`). Владелец,
поделивший 550,17 на 3 500,55, получит «фонд оплаты 15,7 %» — число, не равное ни одной ставке и ни
одной действительной доле: правильный знаменатель здесь 2 500,55 ₽ (касса врачей со ставкой).
Плитки, стоящие в одном ряду, обязаны иметь одну базу или явно называть разную.

**4.3. Удержано (746,90 ₽) больше начисленного (550,17 ₽) — и это нигде не названо.** Само по себе
это и есть краткая формулировка причины отрицательного итога, но на экране оба числа стоят молча,
рядом, без связи.

**4.4. `totals.materialCostRub` считается по другому множеству врачей, чем `withheldMaterialRub`.**
`doctorPayouts.ts:710` — прибавление себестоимости стоит **вне** условия `state === "computed"`, то
есть по всем строкам; удержание (строка 713) — только по посчитанным. В прогоне обе величины совпали
(746,90) лишь потому, что у врача без ставки не было списаний. Как только у врача без ставки
появится расход материалов, два поля ответа разойдутся без пояснения. Экран `totals.materialCostRub`
сейчас не показывает, поэтому это пока дефект контракта, а не картинки.

**4.5. Счётчик `doctorsWithoutRate` назван неверно и даёт неверный совет.**
`doctorPayouts.ts:716-718`: он растёт для **любого** непосчитанного состояния, включая
`material_policy_missing`, где ставка как раз задана и пригодна, а нет процента удержания. При этом
и текст ограничения (`doctorPayouts.ts:723-726` — «у N не задана пригодная ставка»), и подсказка на
экране (`DoctorPayoutDashboard.tsx:525-531` — «Задайте процент врача») уверенно отправляют владельца
править ставку. Для врача в состоянии `material_policy_missing` это работа впустую: ставка у него
верная.

## 5. Что должно быть написано человеку. Готовые формулировки

Порядок в тексте один и тот же: **что произошло → числами почему → похоже ли это на ошибку настройки
→ что сделать**. Числа подставляются сервером, потому что текст строки собирается на сервере
(`payoutRowNote`, `doctorPayouts.ts:309-381`) — это правильное место, менять его не нужно.

### 5.1. Строка врача с отрицательной выплатой (заменяет `doctorPayouts.ts:360-365`)

> Выплаты нет: врач должен клинике 400 ₽. Начислено 100 ₽ — это 10 % от кассы 1 000 ₽. Удержано
> 500 ₽ — это 100 % себестоимости материалов, списанных по оплаченным приёмам. Удержание больше
> начисления, поэтому итог со знаком минус. Это не ошибка расчёта и не требование к врачу доплатить:
> сумма показывает, что материалы этого месяца стоили клинике дороже, чем врач заработал процентом.
> Прежде чем показывать её врачу, проверьте три вещи: цены складских позиций, количество материала в
> правилах списания на услугу и саму ставку. Разговор с врачом — после проверки, а не до неё.

Числа в шаблоне: начислено, ставка, касса, удержано, процент удержания, модуль долга.

### 5.2. Отдельная фраза-диагноз, когда порог безубыточности заведомо низкий

Добавляется к 5.1 при `материалы/касса > c/d` и `d = 100`:

> Похоже на ошибку настройки, а не на факт работы. При ставке 10 % и удержании 100 % себестоимости
> выплата остаётся положительной только пока материалы дешевле 100 ₽ — это 10 % кассы врача.
> Фактически израсходовано 500 ₽, то есть 50 % кассы. При таком сочетании процентов минус будет
> почти каждый месяц, и чинится это в ставке, а не в бухгалтерии.

И, пока нет редактора ставок, ровно одно честное предложение о том, откуда взялись 100 %:

> Удержание 100 % себестоимости система поставила сама, когда врач впервые подписал приём; в
> интерфейсе это значение пока не меняется. Если договорённость с врачом была другой — например
> процент считается после вычета материалов или удерживается только часть себестоимости, — скажите
> об этом администратору системы: расчёт будет неверным каждый месяц.

Это предложение **обязано быть переписано**, когда появится экран ставок. Пока оно единственное
непротиворечивое: см. 3.3 — отправлять в настройки некуда.

### 5.3. Ячейка «К выплате»

Убрать `ops-state--bad`: крест «✕» в денежной колонке — знак ошибки, а не знак долга (2.1). Число
показывать обычным денежным начертанием со знаком минус, второй строкой мелкая подпись
**«долг врача клинике»**. Если нужна цветовая пометка — только та, что не подставляет глиф-крест
(`ops-state--warn` ставит «•», css:358-363), либо отдельный класс без `::before`. Знак минус остаётся:
скрывать его нельзя.

### 5.4. Итог по клинике

Вместо одной плитки «к выплате всего: −196,73 ₽» — два числа, потому что это два разных денежных
события:

> К выплате врачам: 203,27 ₽ (1 врач). Клинике должны врачи: 400 ₽ (1 врач).

И абзац под плитками, которого сейчас нет вовсе:

> Итог со знаком минус означает, что удержания за материалы (746,90 ₽) вышли больше начислений по
> проценту (550,17 ₽). Это не общая сумма к выплате: заплатить −196,73 ₽ нельзя, и долг одного врача
> не покрывает зарплату другого. Смотрите два числа отдельно: 203,27 ₽ клиника отдаёт, 400 ₽ ей
> должны. Если долг появился не однажды, а второй месяц подряд, причина в настройке ставки или в
> ценах склада, а не в работе врача.

### 5.5. Подпись базы у плиток

«касса клиники за месяц» стоит рядом с начислением, посчитанным по другому множеству врачей (4.2).
Подпись должна называть базу: либо показывать «касса врачей со ставкой: 2 500,55 ₽», либо оставить
кассу клиники, но подписать начисление как «начислено по 2 врачам из 3». Иначе деление одной плитки
на другую даёт выдуманный процент фонда оплаты.

### 5.6. Мелкая клиника

Ничего нового прятать за флаг не нужно: экран уже открывается только по серверному праву
`payroll.read` / `payroll.read.own` (`billing.ts:246-258`), а второй числовой блок («клинике должны
врачи») показывается только когда такой долг есть. У клиники без отрицательных строк экран не
меняется вообще.

## 6. Найдено по пути, отдельными дефектами (не входит в вопросы задачи)

**6.1. Себестоимость удерживается повторно при рассрочке — деньги врача.** CTE
`payout_paid_visits` (`doctorPayouts.ts:405-419`) отбирает визиты, у которых **есть оплата в
периоде**, а CTE материалов (`:448-485`) суммирует по такому визиту **все** строки `auto_deduct`, без
фильтра по дате самой строки расхода. Визит, оплаченный в два приёма — задаток в июле и остаток в
августе, — попадает в `payout_paid_visits` **оба** месяца, и полная себестоимость материалов
удерживается **дважды**. При протезировании с рассрочкой это обычный сценарий, а не край. Отдельно:
в первом месяце начисление считается только от задатка, а удержание — от всей себестоимости, что
само по себе гонит строку в минус без всякой ошибки настройки. Это статический вывод из текста
запроса; прогоном на базе я это не измерял.

**6.2. Ставка 0 % превращается в 25 %.** `workspaceProfile.ts:785`:
`(s.percentage ? Number(s.percentage) : 25)`. Ноль ложен, поэтому клиника, сознательно поставившая
0 % (сотрудник на окладе), получит в базе 25 %. При этом `Step5Staff.tsx:355-362` создаёт нового
сотрудника именно с `percentage: 0` — то есть оставленное без правки поле даёт 25 %, а не ноль.

**6.3. Правило списания пишется без организации.** `inventory.ts` вставляет
`procedure_material_rules` без `organizationId` (в `values` его нет), тогда как схема эту колонку
объявляет (`schema.ts:1747`). Чтения фильтруют по владельцу услуги, поэтому сейчас это не течёт, но
колонка остаётся пустой у всех новых правил.
