# Разбор: календарная дата, полученная арифметикой по миллисекундам

Отправная точка — коммит `a61507b76`: маршрут утреннего обзвона считал «завтра в поясе клиники»
как `now + 24 * 60 * 60 * 1000`, а сутки не всегда равны 24 часам. Починка в
`apps/api/src/routes/dayConfirmations.ts` (`dateInTimeZone`, `nextCalendarDay`,
`tomorrowInTimeZone`) — образец: берётся сегодняшняя дата В ПОЯСЕ КЛИНИКИ и к ней прибавляется
один календарный день через `Date.UTC(year, month - 1, day + 1)`.

Здесь — сплошной обзор проекта на этот класс. Просмотрено **52 места** в `apps/api/src` и
`apps/web/src`. Разметка по каждому: **категория** (календарь / длительность), **живой или
теоретический**, вред, починка.

---

## 0. Сначала — факт о часовых поясах, от которого зависит половина вердиктов

Вопрос: возможен ли у клиники пояс с переходом на летнее время? Россия перевод стрелок отменила
в 2014 году, поэтому для `Europe/Moscow`, `Europe/Samara` и прочих российских поясов ошибка
«сутки ≠ 24 часа» не проявится никогда.

**Ответ: нерусский пояс возможен. Пояс ничем не ограничен.** Два факта из кода:

1. `apps/api/src/db/schema.ts:298` — `timezone: text("timezone").notNull().default("Europe/Samara")`.
   Свободная строка, ни перечисления, ни CHECK-ограничения. То же у
   `communication_settings.timezone` (`schema.ts:2408`).
2. `packages/shared/src/index.ts:1386-1400` — единственная проверка значения:
   ```ts
   function isValidTimeZone(value: string): boolean {
     try { new Intl.DateTimeFormat("ru-RU", { timeZone: value }).format(...); return true; }
     catch { return false; }
   }
   export const timeZoneSchema = z.string().trim().min(1).max(80).refine(isValidTimeZone, ...);
   ```
   Проходит ЛЮБОЙ существующий IANA-пояс, включая `America/New_York` и `Europe/Berlin`. Список
   российских поясов нигде не задан.

**Следствие для отчёта.** Находки делятся на две группы, и смешивать их нельзя:

- **Только-DST (теоретические для российской клиники).** Проявляются лишь в поясе с переходом.
  Живые ровно в той мере, в какой схема разрешает такой пояс, — то есть возможные, но ни на одной
  российской клинике не срабатывающие. Так и называю: теоретические.
- **Ошибка пояса как таковая (живые для российской клиники ежедневно).** `toISOString()` даёт день
  по UTC. У Москвы смещение +3, у Самары +4, у Камчатки +12 — и оно ПОЛОЖИТЕЛЬНОЕ у всех
  российских поясов. Значит день по UTC отстаёт от местного каждую ночь: в Москве с 00:00 до 03:00,
  в Самаре до 04:00, на Камчатке — половину суток. Это не про переход на зимнее время вообще; это
  срабатывает сегодня, у всех, каждый день. Таких находок больше, и вред от них выше.

Задание просило искать `toISOString().slice(0, 10)` там, где нужна дата в поясе клиники, — вот эта
вторая группа и есть главный урожай.

### 1.1 `apps/web/src/components/schedule/DayConfirmationsPanel.tsx:77-81` — починка ведущего не работала

```ts
function tomorrowIsoDate(): string {
  const tomorrow = new Date(Date.now() + 24 * 60 * 60 * 1000);
  ...
}
```

**Категория: календарь.** Результат — начальное значение поля «День» и `?date=` в запросе.

**Живой, и хуже того: он обесценивал `a61507b76`.** Панель ВСЕГДА посылала явную дату
(`?date=${date}`), поэтому серверная ветка «даты нет — считаю завтра в поясе клиники»
(`tomorrowInTimeZone`) в рабочем пути не исполнялась ни разу. Правильный расчёт на сервере был, а
администратор всё равно получал день, посчитанный браузером.

Два дефекта в четырёх строках:
1. `+ 24 * 60 * 60 * 1000` — тот же класс, что починил ведущий: в поясе с переходом на зимнее
   время не доводит до следующей календарной даты.
2. `getFullYear/getMonth/getDate` — день по поясу БРАУЗЕРА, а не по `clinics.timezone`. Планшет
   регистратуры с неверно выставленным поясом, или клиника, чей пояс отличается от пояса машины,
   дают список не того дня без единого сообщения на экране.

**Вред:** администратор обзванивает не тот день; завтрашние приёмы остаются без подтверждения.

**Починка:** дату для начальной загрузки клиент не считает вообще. Первый запрос идёт без
`?date=`, сервер отвечает полем `date` — уже в поясе клиники и уже календарно, — и это значение
становится значением поля ввода. Клиентский расчёт дня удалён, а не исправлен: второй ответ на тот
же вопрос не нужен.

**Сторож:** `apps/web/src/tests/dayConfirmationsPanelDefaultDay.test.ts`.

### 1.2 `apps/web/src/AppHelpers.tsx:1005-1013` — день по UTC в датах медицинских документов

```ts
export function todayDateInputValue(): string {
  return new Date().toISOString().slice(0, 10);
}
export function dateInputValuePlusDays(days: number): string {
  const date = new Date();
  date.setDate(date.getDate() + days);
  return date.toISOString().slice(0, 10);
}
```

**Категория: календарь.** Это прямо дата в поле ввода типа `date`, не длительность.

**Живой у КАЖДОЙ российской клиники, каждую ночь.** `setDate` шаг делает верно (это календарная
операция), но `toISOString()` обратно уводит в UTC. В Москве с 00:00 до 03:00 местного времени обе
функции отдают вчерашнее число, в Самаре (пояс по умолчанию, +4) — до 04:00, на Камчатке — до
12:00, то есть половину суток.

**Куда попадает значение — и почему это хуже, чем выглядит.** `todayDateInputValue()` заполняет
`outpatient025uOpenedAt` (дата открытия карты 025/у), `recordExtractPeriodStart` и
`recordExtractPeriodEnd` (период выписки из медкарты) — `AppHelpers.tsx:1015-1029` и `1115-1119`.
Эти черновики — начальное состояние документа (`useAppLogic.tsx:5740`, `5822`).

В проекте УЖЕ есть правильный расчёт того же дня: `documentLogic.ts:83`
`withDocumentCreationTimestamps` собирает `asIsoDate` из `getFullYear/getMonth/getDate` и в
комментарии называет ровно эту ошибку. Но он заполняет только ПУСТЫЕ поля («Значения, введённые
руками, не трогаются»). Предзаполненное неверное число пустым не является — и правильный расчёт
молча уступает неправильному. Сторож `apps/web/src/tests/documentCreationTimestamps.test.ts`
проходит, потому что вызывает функцию с явно пустым полем; рабочий путь он не покрывает.

`dateInputValuePlusDays` тем же способом считает сроки оплаты и график платежей
(`useAppLogic.tsx:11587`, `11605`, `11613`).

**Вред:** медицинский и юридический документ с датой на день раньше. Карта 025/у — форма
государственного учёта, период выписки из медкарты — основание для страховой и для суда.
«Плюс-минус день» здесь не помеха удобству, а расхождение документа с фактом.

**Починка:** день берётся из местных полей `Date`, как в `withDocumentCreationTimestamps`. Обеим
функциям добавлен необязательный параметр `timeZone`: когда пояс клиники вызывающему известен,
день считается в нём через `Intl.DateTimeFormat("en-CA", { timeZone })`. Подпись расширена, а не
изменена, — поэтому ни один вызывающий не тронут (в том числе `useAppLogic.tsx`, который сейчас
правит другой агент).

**Сторож:** `apps/web/src/tests/dateInputValueLocalDay.test.ts`.

### 2.5 `apps/api/src/services/reports/managerReports.ts:56-60` — месяц отчёта в поясе сервера — ЗАКРЫТО `6b19e4491`

```ts

const to = new Date(now.getFullYear(), now.getMonth() + 1, 0, 23, 59, 59, 999);
```

**Категория: граница периода.** Календарная арифметика верна (`new Date(y, m + 1, 0)` — законный
приём для последнего дня месяца). Дефект в другом: границы берутся в поясе СЕРВЕРА, а не клиники.
Живой для клиники, чей пояс отличается от серверного: выручка первых часов первого числа попадает в
предыдущий месяц. То же у `routes/analytics.ts:56-62`.

### 3.1 `apps/web/src/AppHelpers.tsx:4470` — точная форма починенного дефекта

## 7. `date_trunc` И `extract` В ОТЧЁТАХ: ДОКАЗАНО ПРОГОНОМ, НЕ ПОЧИНЕНО

Раздел 6 честно пометил это непроверенным. Проверено — прогоном по живой PostgreSQL 18 на
`127.0.0.1:5432`, read-only, без DDL и без записи. Мгновение под проверкой — `2026-07-29T22:00:00Z`
(по UTC ещё 29 июля, в Самаре и на Камчатке уже 30-е).

```
--- SET TIME ZONE 'UTC' ---
  date_trunc('day')  : 2026-07-29 00:00:00
  date_trunc('month'): 2026-07-01 00:00:00
  isodow / hour      : 3 / 22
--- SET TIME ZONE 'Europe/Samara' ---
  date_trunc('day')  : 2026-07-30 00:00:00
  date_trunc('month'): 2026-07-01 00:00:00
  isodow / hour      : 4 / 2
--- SET TIME ZONE 'Asia/Kamchatka' ---
  date_trunc('day')  : 2026-07-30 00:00:00
  date_trunc('month'): 2026-07-01 00:00:00
  isodow / hour      : 4 / 10
```

**Зависимость от пояса СЕССИИ подтверждена**, и она шире, чем назвал раздел 6:

- `date_trunc('day', ...)` — корзина дня в `revenueTimeline` (`managerReports.ts:86-95`) съезжает.
- `extract(isodow ...)` и `extract(hour ...)` — **`scheduleLoad` (`managerReports.ts:1010-1011`,
  `1024`), которого в разборе не было вовсе.** Тепловая карта «когда открывать смены» сдвигается на
  ВСЮ величину смещения: один и тот же приём попадает в 22 часа, в 2 часа или в 10 часов в
  зависимости от пояса сессии, а день недели меняется со среды на четверг. Это самое вредное из
  трёх: решение «куда ставить дополнительное кресло» принимают по этой карте.
- `date_trunc('month', ...)` в `patientFlow` (`:647`, `:663`) в этом примере не сдвинулся — месяц
  устойчивее дня, сдвигается только у мгновений в первых/последних часах месяца.

**ПОЧЕМУ ЭТО СЕГОДНЯ НЕ ГОРИТ, И ЭТО НАДО СКАЗАТЬ ПРЯМО.** Пояс сессии пула приложения, замеренный
тем же прогоном, — `Europe/Samara`. Он совпадает со значением `clinics.timezone` по умолчанию,
поэтому для клиники по умолчанию корзины СЕЙЧАС верны. Верны они по совпадению настройки
`postgresql.conf` со схемой, а не потому, что код это утверждает: смена `TimeZone` на сервере или
переезд базы молча перебросит все корзины во всех отчётах. Живой дефект — у любой клиники, чей пояс
отличается от `Europe/Samara` (московская: корзины считаются при +4 вместо +3, и платежи с 00:00 до
01:00 по Москве попадают в корзину предыдущего дня).

**ПОЧЕМУ НЕ ПОЧИНЕНО В ЭТОМ ЗАХОДЕ.** Починка — переписать выражения на
`... AT TIME ZONE $пояс` и протащить пояс в `ReportScope`. Приём проверен тем же прогоном и работает
без изменения пояса сессии:

```
AT TIME ZONE 'UTC'           : day=2026-07-29 isodow=3 hour=22
AT TIME ZONE 'Europe/Samara' : day=2026-07-30 isodow=4 hour=2
AT TIME ZONE 'Asia/Kamchatka': day=2026-07-30 isodow=4 hour=10
```

Но тем же прогоном найдена ловушка, из-за которой этого нельзя делать без отдельного гейта:

```
unknown zone raises: 22023 time zone "Марс/Олимп" not recognized
```

`clinics.timezone` — свободный текст, а единственная проверка при записи (`timeZoneSchema`,
`packages/shared/src/index.ts:1386-1400`) спрашивает ICU, а не Postgres. `pg_timezone_names` на этом
сервере знает 598 имён; ICU знает больше. Значит клиника с поясом, который ICU принял, а Postgres не
знает, получит `22023` — и ВОСЕМЬ работающих отчётов руководителя превратятся в 500. Менять
арифметику отчёта о деньгах, заведомо создавая путь к отказу, без гейта на `pg_timezone_names` и без
сквозного прогона каждого маршрута в двух поясах — нельзя. Это отдельная работа со своим
доказательством, а не хвост этой.

Что нужно следующему заходу: гейт «пояс известен Postgres» (одна выборка из `pg_timezone_names`,
кешируется на процесс), `timeZone` в `ReportScope`, переписанные выражения в `revenueTimeline`,
`patientFlow` и `scheduleLoad`, и сквозной прогон восьми маршрутов `/api/reports/*` для клиники в
поясе, отличном от серверного.
