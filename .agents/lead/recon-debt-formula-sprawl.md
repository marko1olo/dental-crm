## 0а. Мои собственные ошибки в этом заходе — первыми

Три, все найдены и исправлены ДО коммита, но каждая была настоящей.

**1. Я едва не создал десятую копию денег.** Первую версию `apps/api/src/money/patientDebt.ts`
я написал с собственным разбором копеек, форматированием и сложением — не найдя
`packages/shared/src/utils/money.ts`, который делает ровно это и на который в дереве уже стоит
явный запрет второй копии: `apps/api/src/documents/guards.ts:49` —
«Считать деньги здесь теперь нечем, кроме `packages/shared/src/utils/money.ts`; третьей копии
не создаётся». То есть в задаче про устранение дублирующей арифметики первым дублирующим
оказался я. Причина промаха названа честно: я искал по именам величин долга (`buildBillingSummary`,
`balanceRub`, `receivables`) и не сделал сплошного поиска по денежным примитивам. Модуль
переписан: копейки, разбор, сложение, умножение и печать берутся импортом из `@dental/shared`,
свой остался только слой долга, и каждое его отличие от общего названо в комментарии поимённо
(их три, и все три — сужение, а не другое поведение).

**2. `clinicDebtTotals` молча возвращал НУЛИ.** Подпись была `Iterable<PatientLedger>`, а
`buildPatientLedgers` возвращает `Map`. `for (… of map)` перебирает пары `[ключ, значение]`,
поэтому `balanceKopecks` был `undefined`, `Math.max(0, NaN)` дал `NaN`, `NaN >= порог` — `false`,
и все три итога вышли нулями: «долгов в клинике нет». Дефект того же класса, что
`patientsQuery.ts:67`, из-за которого этот файл вообще написан. Поймал его ТЕСТ, не типизация:
`tsx` типы не проверяет, а `tsc` в `apps/api` исключает `*.test.ts`. Закрыто двумя рубежами —
`Map` разворачивается явно, и форма каждого сальдо проверяется с броском.

**3. Тест сравнивал суммы ASCII-пробелом.** Печать денег использует НЕРАЗРЫВНЫЙ пробел
(U+00A0), и падение выглядело как `'3 100,50' !== '3 100,50'` — два визуально одинаковых
значения. Правильным было поведение печати, а не теста; исправлен тест, разделитель берётся
из общего `RU_MONEY_NBSP`, а не пишется невидимым литералом.

Отдельно: `npx tsc --noEmit` в `apps/api` **не проверяет тесты** — `tsconfig.json` исключает
`src/tests` и `src/**/*.test.ts`. Для тестов есть `tsconfig.tests.json` (`npm run
typecheck:tests`). Заявлять «tsc чисто», прогнав только первый, значит не проверить половину
своей работы.

## 1. Числа с живых данных: все формулы на одном наборе

Все суммы получены прямым SQL, точным `numeric`, без плавающей точки. Скрипт под каждым
числом — реальный, я его прогнал.

```
+-[ RECORD 1 ]-------------+-----------+
| A_dashboard_totalDue     | 51400.00  |   <- #3 buildBillingSummary
| B_receivables_totalDebt  | 53000.00  |   <- #1 receivables.totalDebtRub
| B2_totalPrepaid          | 1600.00   |   <- #2 receivables.totalPrepaidRub
| B_minus_B2               | 51400.00  |   <- сходимость: 53000 − 1600 = 51400 = A
| C_sum_balanceRub_rounded | -51400    |   <- #5 domainStateHydration, знак обратный
| C_sum_balance_exact      | -51400.00 |
| E_planned_TPB            | 118800.00 |   <- #9 TreatmentPlanBuilder, СЕГОДНЯ совпадает
| planned_canon            | 118800.00 |
| planned_raw_qty          | 118800.00 |
| paid_total               | 67400.00  |
+--------------------------+-----------+
```

**Главное расхождение подтверждено числом: 53 000,00 против 51 400,00 — ровно 1 600,00.**
Это две переплаты по 800,00 ₽. Главный экран молча зачёл их в чужой долг, отчёт дебиторки —
нет. Оператор видит две суммы и не знает, какой верить. Администратор, звонящий по отчёту
дебиторки, назовёт пациенту сумму, которой на главном экране нет.

Разбор по пациентам (тот же прогон, `full outer join` — пациент может быть только в одной
из двух таблиц):

```
| planned  |   paid   | B_debt(planned-paid) |  B_in_report  | C_balanceRub | D_balanceRub |
| 41300.00 | 14800.00 | 26500.00             | 26500.00      | -26500       | 0            |
| 33700.00 | 7200.00  | 26500.00             | 26500.00      | -26500       | 0            |
| 5400.00  | 5400.00  | 0.00                 | -- dropped -- | 0            | 0            |
| 7200.00  | 7200.00  | 0.00                 | -- dropped -- | 0            | 0            |
| 5400.00  | 5400.00  | 0.00                 | -- dropped -- | 0            | 0            |
| 21200.00 | 22000.00 | -800.00              | -- dropped -- | 800          | 0            |
| 4600.00  | 5400.00  | -800.00              | -- dropped -- | 800          | 0            |
```

Читается это так: **два пациента переплатили по 800 ₽ и не видны ни в одном отчёте долга**,
а `#6` (`patientsQuery.ts`) на всех семи строках отвечает `0` — то есть API картотеки
утверждает, что клинике не должен никто и клиника не должна никому.

SQL целиком (я прогонял его через `\i`, поэтому воспроизводится дословно):

```sql
with planned as (
  select patient_id,
         sum(greatest(unit_price_rub * greatest(quantity,1) - discount_rub, 0))::numeric(12,2) as planned_sql,
         sum((unit_price_rub - discount_rub) * greatest(quantity,1))::numeric(12,2)            as planned_tpb
    from treatment_items
   where organization_id = :'org' and status <> 'cancelled'
   group by patient_id
), paid as (
  select patient_id, sum(amount_rub)::numeric(12,2) as paid_rub
    from payments
   where organization_id = :'org' and status = 'paid'
   group by patient_id
), bal as (
  select coalesce(pl.patient_id, pa.patient_id) as patient_id,
         coalesce(pl.planned_sql,0) as planned_sql, coalesce(pl.planned_tpb,0) as planned_tpb,
         coalesce(pa.paid_rub,0)    as paid_rub,
         (coalesce(pl.planned_sql,0) - coalesce(pa.paid_rub,0)) as debt
    from planned pl full outer join paid pa on pa.patient_id = pl.patient_id
)
select greatest(0, (select sum(planned_sql) from bal) - (select sum(paid_rub) from bal))    as "A_dashboard_totalDue",
       (select coalesce(sum(debt),0)  from bal where  debt >= 1)                            as "B_receivables_totalDebt",
       (select coalesce(sum(-debt),0) from bal where -debt >= 1)                            as "B2_totalPrepaid",
       (select coalesce(sum(round(paid_rub - planned_sql)),0) from bal)                     as "C_sum_balanceRub_rounded",
       (select coalesce(sum(planned_tpb),0) from bal)                                       as "E_planned_TPB";
```

### 1.1. Скрытые расхождения: сегодня 0 ₽, потому что данные их не задевают

Три расхождения на СЕГОДНЯШНИХ данных дают ноль. Это не «их нет» — это «их пока нечем
поймать», и такой вердикт обязан быть отделён от проверенного расхождения выше.

**Формула строки `#9` против канона.** Разность двух выражений равна ровно
`скидка × (кол-во − 1)`. Прогон на живых строках:

```
|       scenario        | canon_minus_TPB |
| today (live quantity) | 0.0000          |
| same rows, quantity 2 | 1600.00         |
| same rows, quantity 3 | 3200.00         |
```

Живые данные: `min(quantity)=1.00, max(quantity)=1.00, строк с quantity<1: 0, дробных: 0,
cancelled: 0`. Две строки из десяти несут скидку 800 ₽ (`7200−800` и `5400−800`). Достаточно
администратору поставить количество 2 на этих двух строках — и `#9` разойдётся с каноном на
1 600 ₽. Это уже произошло бы в акте выполненных работ, потому что `#9` — единственный
расчёт, который **пишет** баланс, а не читает.

**Страховое покрытие: сервер против веба.** `useAppLogic.tsx:5171` считает
`totalDueRub = назначено − ПОКРЫТИЕ − оплачено`, а `sampleData.ts:1349` — `назначено − оплачено`.
Поле называется одинаково, и его же гарантия сходимости записана в контракте
(`packages/shared/src/tests/money-contract-kopecks.test.ts:448-462`: «долг остаётся суммой
частей: план минус покрытие минус оплата»). То есть **сервер нарушает собственный контракт
сходимости**: он вообще не отдаёт `insuranceCoverageRub`
(`billingSummarySchema` объявляет его `.optional()`, `packages/shared/src/index.ts:2065`).
Расхождение сегодня — 0 ₽, по двум независимым причинам сразу, обе проверены SQL:
`select count(*) from insurance_contracts` → **0**, и все 10 живых позиций попадают в
категорию `other`, которой веб-код назначает `pct = 0`. Первый же заведённый договор ДМС
разведёт два экрана.

**Округление до рубля в `#5`.** `Math.round(paid − planned)` на живых данных даёт ровно
−51 400, потому что ни одна живая сумма не имеет копеек: `count(*) filter (where amount_rub
<> round(amount_rub))` = **0** по платежам и **0** по ценам и скидкам позиций. Копейки
уже разрешены и колонкой `numeric(12,2)`, и контрактом (`moneyRubSchema`), и сквозной проверкой
`chainWeldProof.ts:325` платит 1 500,50 ₽. Арифметика потери измерена:
`Math.round(-49899.5) = -49899`, `Math.round(49899.5) = 49900`. Округление **несимметрично
по знаку**: должнику 50 копеек прощают, переплатившему — приписывают. Это не «то же самое с
точностью до рубля», это две разные ошибки в зависимости от того, кто кому должен.

## 2. Место за местом: что складывается, что вычитается, вердикт

### #1 — `apps/api/src/services/reports/managerReports.ts` — `receivables()` → `totalDebtRub`

* `:1107` объявление, `:1118` сумма назначенного, `:1145` баланс, `:1152` фильтр должников,
  `:1218` итог.
* Строка позиции (SQL, точный `numeric`):
  `greatest(unit_price_rub * greatest(quantity, 1) - discount_rub, 0)`
* Отбор позиций: `organization_id = :org AND status <> 'cancelled'`.
* Оплата: `sum(amount_rub) where status = 'paid'`, группировка по пациенту.
* Баланс пациента: `назначено − оплачено`. Положительный — долг.
* Итог: `Σ` по пациентам, **у которых баланс ≥ minDebtRub (по умолчанию 1 ₽)**, затем
  `Math.round(… * 100) / 100`.
* Объединение пациентов: `[...new Set([...planned.keys(), ...paid.keys()])]` — пациент,
  заплативший вперёд до любых назначений, иначе не виден вовсе.
* На живых данных: **53 000,00**.

**ВЕРДИКТ: КАНОН.** Причины, по которым канон именно здесь, а не на главном экране:

1. Это единственный расчёт, который считает **по пациенту**, а долг — величина пациента, а
   не клиники. Клиника не «должна себе» — должны конкретные люди, каждому из которых звонят
   отдельно.
2. Это единственный расчёт, который **не смешивает переплату одного с долгом другого**.
   Деньги пациента А не гасят обязательство пациента Б ни юридически, ни бухгалтерски.
3. Арифметика идёт в `numeric` на стороне PostgreSQL, а не в плавающей точке JS: приведение
   `::numeric(12,2)` стоит на уровне суммы, копейки сохраняются точно.
4. `greatest(…, 0)` не даёт отрицательной строке (скидка больше цены) тайно уменьшить долг по
   другим позициям того же пациента.
5. Отчёт **сам печатает** сходимость с главным экраном (`:1226-1235`,
   `«53 000,00 − 1 600,00 = 51 400,00 ₽»`), то есть автор уже знал про расхождение и назвал его.

Слабое место канона, названное честно: порог `minDebtRub ≥ 1 ₽` отбрасывает долги меньше
рубля. Это осознанный шум-фильтр, а не ошибка, но он означает, что `Σ` строк отчёта — это НЕ
полная дебиторка. В моём модуле порог остался, вынесен в параметр и назван.

### #2 — тот же файл — `receivables()` → `totalPrepaidRub`

* `:1159` отбор переплативших (`-debt >= minDebtRub`), `:1164` итог.
* Формула: `Σ (оплачено − назначено)` по пациентам с переплатой ≥ 1 ₽, округление до копейки.
* На живых данных: **1 600,00** у **2** пациентов.

**ВЕРДИКТ: КАНОН, ИНАЯ ВЕЛИЧИНА.** Это не долг и не «отрицательный долг»: это обязательство
клиники вернуть деньги. Правильное имя — **«сколько клиника должна пациентам»**. До появления
этого числа переплативший пациент просто исчезал из всех отчётов: `#1` его отбрасывал
фильтром, а `#3` тихо зачитывал его деньги в чужой долг.

### #3 — `apps/api/src/sampleData.ts:1291-1355`, поле `totalDueRub` на `:1349`

* Строка позиции: `treatmentLineTotal` (`:1284`) =
  `Math.max(0, roundToKopecks(unitPriceRub * quantity - discountRub))`.
  Количество берётся **сырым**, без `greatest(quantity, 1)`.
* Отбор: `status !== "cancelled"`, **по всем позициям модульного состояния**, без разбивки
  по пациенту.
* Оплата: `Σ amountRub where status === "paid"` — тоже по всей клинике.
* Итог: `Math.max(0, roundToKopecks(totalPlannedRub - totalPaidRub))`.
* На живых данных: **51 400,00**.

**ВЕРДИКТ: ИНАЯ СЕМАНТИКА.** Это не долг пациентов. Это **нетто-остаток клиники: сколько
денег клиника ещё не собрала, после зачёта переплат**. Величина законная — бухгалтеру она
нужна, — но названа неправильно: слово `Due` и подпись «долг» на экране
(`ShiftView.tsx:751`, `FinancePlanning.tsx:61`) обещают ответ на вопрос «сколько должны
пациенты», а отдают ответ на другой вопрос. Правильное имя — **«не собрано, нетто»**.

Разница с каноном не сводится к округлению: `51 400 = 53 000 − 1 600`, то есть ровно на
величину переплат. `Math.max(0, …)` вокруг итога маскирует ещё и предельный случай: если
переплаты когда-нибудь превысят долги, экран покажет `0` вместо «клиника должна вернуть
столько-то».

### #4 — `apps/api/src/sampleData_opt.ts:1068-1098`, `totalDueRub` на `:1087`

**Приговор `sampleData_opt.ts`: это не «оптимизированная версия» и не запасной путь.** Это

patient lookup in review request loop`), 9 343 строки против 12 657 у живого файла, никем не
импортируемый и исключённый из обоих tsconfig. Он опаснее обычного мёртвого кода: агент,
искавший `buildBillingSummary` через `rg`, находит ДВЕ реализации, и половина шансов, что он
правит мёртвую. Именно это и есть механизм размножения формул. **Он подлежит удалению
отдельным коммитом** — не моим, потому что мне разрешены только мои новые файлы, и удаление
429 КБ рядом с работающими агентами столкнётся с их правками.

Числом: на живых данных `#4` и `#3` дают ОДИНАКОВЫЕ 51 400,00 — потому что ни одна живая

### #9 — `apps/api/src/treatment/TreatmentPlanBuilder.ts:124-142`


**ВЕРДИКТ: ИНАЯ ФОРМУЛА СТРОКИ — и это единственное место, которое долг ЗАПИСЫВАЕТ.**

* `(цена − скидка) × количество` против канонического `цена × количество − скидка`.
  Разность ровно `скидка × (количество − 1)`. На живых строках со скидкой 800 ₽ при
  количестве 2 это **1 600,00 ₽**, при количестве 3 — **3 200,00 ₽** (SQL-прогон в разделе 1.1).
  Какая из двух формул права, решает прайс: скидка в этом проекте задана строкой позиции
  (`treatment_items.discount_rub`), а не ценой за единицу, значит вычитать её надо один раз
  из итога строки — канон прав, `#9` умножает скидку на количество.
* Единственное честное место в девяти: считает через `Decimal`, а не в плавающей точке.
* Нет `Math.max(0, …)` на строке: отрицательная строка (скидка больше цены) тайно уменьшит
  итог акта.
* Пишет `patient.balanceRub` инкрементально (`баланс − сумма акта`), тогда как `#5` тот же
  `balanceRub` **пересчитывает с нуля** при каждой гидратации. Две записи в одно поле с
  разной арифметикой: инкремент затирается следующей гидратацией, и результат зависит от
  того, чей запрос пришёл последним.

## 3. Сколько РАЗЛИЧИМЫХ величин на самом деле: пять, поверх одной первичной

Девять расчётов отвечают на пять разных вопросов оператора. Всё остальное — дубли и порча.

| Вопрос оператора | Величина | Кто сегодня отвечает | Живое число |
|---|---|---|---|
| «Сколько ЭТОТ пациент должен клинике?» | долг пациента, ≥ 0 | `#7`, `#8` (с дефектами) | 26 500,00 / 0,00 |
| «Сколько клиника должна ЭТОМУ пациенту?» | переплата пациента, ≥ 0 | никто (только строка в `#2`) | 800,00 |
| «Сколько всего должны пациенты?» | дебиторка клиники | `#1` | **53 000,00** |
| «Сколько всего клиника должна вернуть?» | обязательство возврата | `#2` | **1 600,00** |
| «Сколько клиника ещё не собрала, нетто?» | нетто-остаток | `#3` | **51 400,00** |

Первичная величина одна: **сальдо пациента со знаком** = `назначено − оплачено`. Все пять
получаются из неё без новой арифметики: `max(0, сальдо)`, `max(0, −сальдо)` и две суммы плюс
их разность. Именно поэтому девять расчётов — это не девять мнений, а одна формула,
переписанная девять раз с разными потерями.

Что НЕ является отдельной величиной, хотя выглядит ею:
* `#5` — то же сальдо с обратным знаком и округлением до рубля. Не величина, а испорченная копия.
* `#6` — не величина, а ноль.
* `#4` — не величина, а мёртвый снимок `#3`.
* `#+0` (веб со страховкой) — **является** шестой величиной, но она не серверная и в мой
  модуль не входит: покрытие считается по данным договора ДМС, которых сервер в сводку не
  отдаёт вовсе. Это отдельная задача, и её надо ставить как задачу, а не как «поправить долг».

## 4. Что сделано в этом заходе

Новый модуль `apps/api/src/money/patientDebt.ts` — один дом для формулы. Ровно пять
именованных ответов поверх одной первичной величины (сальдо), вся арифметика в **целых
копейках**.

Копейки НЕ реализованы заново: `Kopecks`, `parseKopecks`, `sumKopecks`, `multiplyKopecks`,
`kopecksToNumericString`, `formatKopecksRu`, `RU_MONEY_NBSP` берутся импортом из
`@dental/shared` (`packages/shared/src/utils/money.ts`) — единственного владельца денег в
репозитории. Свой слой сужает общий ровно в трёх местах, и каждое сужение проверено тестом
с числом:

| Общий модуль | Слой долга | Почему |
|---|---|---|
| `parseKopecks(1500.505)` = `150051` (округляет через `toFixed(2)`) | бросает | сглаженная грязь неотличима от факта; расчёт долга обязан УЗНАТЬ о потере точности |
| `parseKopecks(null)` = `0`, `parseKopecks("")` = `0` | бросает | «сумма не пришла» и «лечение бесплатное» — разные факты, а колонки `not null` |
| `multiplyKopecks(цена, 0)` = `0` | бросает | позицию без объёма надо помечать `cancelled`, а не выставлять счёт |

Грязь ниже копейки (`1500.505`, `4500.299999999999`, `3491.4900000000002`) отвергается
исключением `MoneyPrecisionError`: молчаливое округление денег и есть тот дефект, который
девять раз дал девять ответов.

Тесты: `apps/api/src/money/patientDebt.test.ts` — 49 тестов, 15 наборов. Для КАЖДОЙ из девяти
прежних формул рядом стоит её арифметика в чистом виде, и тест показывает расхождение ЧИСЛОМ.
Проверка «моя функция вернула 53000» одна ничего не стоила бы: она прошла бы и на неверной
формуле.

**Вызывающие в этом заходе НЕ переведены.** Модуль подключён только к своим тестам. Это
решение ведущего: переезд разложен на волну по одному файлу на инженера, чтобы не столкнуться
с агентами, работающими в `managerReports.ts` и `visitsQuery.ts` прямо сейчас.
