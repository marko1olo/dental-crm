# Разбор: `treatment_items` против `treatment_plan_items_new` — одна сущность или две

Дата разведки: 2026-07-29. HEAD на момент разведки: `a3a0d45d5`.
База: PostgreSQL 18 на `127.0.0.1:5432`, БД `dental_crm`.
Живые данные на входе: `treatment_items` — **10** строк, `treatment_plan_items_new` — **0**,
`treatment_plans` — **0**.

Разбор написан ДО правки и коммитится отдельно от неё: если правку не примут, ответ на вопрос
«куда должен писать план лечения» останется в дереве, и следующий инженер не будет выбирать заново.

Родственный разбор, обязательный к прочтению перед любой правкой денег:
`.agents/lead/recon-debt-formula-sprawl.md` (девять расчётов долга, единый дом
`apps/api/src/money/patientDebt.ts`, коммит `8062e6d55`).

---

## 0. Мои собственные ошибки в этом заходе — первыми

**1. Я начал с неверной гипотезы и держал её до первого запроса к живым данным.** Постановка
предлагала развилку «назначено в плане против фактически выполненного на приёме», и это звучало
убедительно: у `treatment_items` есть `visit_id`, значит «выполнено на приёме». Живые данные
развилку сломали: все 10 строк стоят в статусе `completed`, а денежные читатели фильтруют
`status <> 'cancelled'`, то есть считают и `proposed`. Читатель, который считает «предложенное»,
не может читать таблицу «только выполненного». Гипотеза «две сущности: план и факт» неверна, и
дальше я вёл разведку по столбцам и читателям, а не по названиям.

**2. Я почти записал вывод «деньги читают НЕ ТУ таблицу».** Это второй вариант из постановки, и
он выглядел логичным, пока я не открыл `apps/api/src/db/domainStateHydration.ts:591-611`. Там
строки таблицы `treatment_items` превращаются в доменный тип `TreatmentPlanItem` и кладутся в
состояние под ключом `"treatmentPlanItems"`. То есть таблица «позиции лечения» И ЕСТЬ позиции
плана лечения для всего приложения, а деньги читают ровно её. Вывод «читатели неправы» был бы
ложным, и по нему пошли бы править восемь файлов вместо одного.

**3. Я едва не заявил потерю копеек там, где её нет.** Итог маршрута считается в плавающей точке
(`odontogram.ts:391-395`), и я собирался назвать `3491,49` пострадавшим. Проверил числом:
`1500.5 + 1990.99 = 3491.49` ровно, `String()` даёт `"3491.49"`. На ЭТОЙ паре потери нет.
Потеря на этом выражении реальна, но на другой форме входа: `1500.10 * 3 = 4500.299999999999`,
то есть её даёт `price * quantity` при количестве больше единицы. Заявлять надо то, что
измерено, а не то, что похоже.

## 1. Короткий ответ

**Две РАЗНЫЕ сущности. Лишней таблицы нет — удалять нечего.** Но развилка проходит не там, где
её предполагала постановка:

| | `treatment_items` | `treatment_plan_items_new` |
|---|---|---|
| Что это | **бухгалтерская книга лечения пациента**: одна строка = одно обязательство пациента заплатить | **строка сметы-документа**: одна строка = одна услуга в подписываемом плане, разложенном по этапам |
| Чей ребёнок | пациента (`patient_id not null`) и, опционально, приёма (`visit_id`) | плана-документа (`plan_id not null`), у самой строки пациента НЕТ |
| Жизненный цикл | есть: `status` — `proposed → approved → in_progress → completed → cancelled` | **нет колонки `status` вообще** |
| Этапность | нет | `phase` 1..12, `is_bundle` |
| Деньги читают | **да, все восемь читателей** | нет ни один |
| Кто пишет в боевом коде | **никто** (только демо-сеялка и тесты) | `routes/odontogram.ts` |

Разделение «назначено против выполнено» существует, но оно живёт ВНУТРИ `treatment_items`, в
колонке `status`, и момент перехода уже имеет владельца: `apps/api/src/routes/diary.ts:285`
ставит `status = 'completed'` всем позициям визита при закрытии дневника приёма. Второй таблицы
для этого не нужно и не было задумано.

Отсюда правка: **писатель плана обязан материализовать позиции в `treatment_items` в той же
транзакции**, статусом `proposed` (или `approved`, если план подписан пациентом). Читателей
денег трогать не надо — они читают правильную таблицу. Третья таблица не заводится, второй
писатель не заводится: в боевом коде писателя в `treatment_items` нет вовсе, поэтому маршрут
плана становится ПЕРВЫМ и единственным.

## 2. Столбцы: живая база, а не только `schema.ts`

Взято из `information_schema.columns`, потому что `schema.ts` в этом дереве
недообъявляет колонки (раздел 8).

### `treatment_items` — 17 колонок живьём

```

visit_id               uuid          null                <- на каком приёме; пусто до приёма
service_id             uuid          null                <- FK на прайс service_catalog_items
```

Значения перечисления: `proposed`, `approved`, `in_progress`, `completed`, `cancelled`.

Три вещи здесь решают вопрос сущности, и все три — против версии «это таблица выполненного»:

   Тип в базе назван по ПЛАНУ лечения.
2. **Значение по умолчанию — `proposed`.** Таблица «фактически выполненного» не имела бы

3. **Две колонки с приставкой `planned_`:** `planned_doctor_user_id`, `planned_chair_id`. Это
   поля планирования — кто и в каком кабинете БУДЕТ делать.

### `treatment_plan_items_new` — 12 колонок живьём

```
id                uuid          not null
plan_id           uuid          not null            <- ребёнок плана-документа
tooth_number      integer       null                <- зуб ЧИСЛОМ по FDI (не text!)
price_id          text          null                <- строка прайса, БЕЗ FK
quantity          integer       not null            <- только целое

discount          numeric(12,2) not null

commission_amount numeric(12,2) not null default 0  <- в schema.ts НЕ объявлена
organization_id   uuid          null                <- НУЛЛЯБЕЛЬНА и маршрутом не заполняется
created_at        timestamptz   null
```

Чего здесь нет и почему это закрывает вопрос:

* **нет `status`** — отменить позицию сметы нечем, а все девять расчётов долга начинаются с
  `status <> 'cancelled'`;
* **нет `patient_id`** — а дебиторка группируется по пациенту (`managerReports.ts:1125`);
* **нет `visit_id`** — а сумма счёта фильтрует позиции по визиту

* **`organization_id` нуллябельна** — а каждый денежный читатель фильтрует по организации;
  маршрут плана её не заполняет, и `chainReconProof.ts:108` считает такие строки отдельным
  числом `plan_items_new_without_org`.

Зато есть `phase` и `is_bundle`, которых нет у `treatment_items`. Это и есть собственная работа
этой таблицы: разложить подписываемую смету по этапам.

## 4. Откуда пришли живые 10 строк `treatment_items` — отпечаток совпал полностью

**Источник: `apps/api/src/scripts/seedOpsScreenshotDemo.ts:435`, демонстрационная сеялка для
снимков экрана.** Это не боевой путь и не остаток чьей-то работы: сеялка вызывается руками.

Улика — не название файла, а отпечаток данных. Сеялка перебирает завершённые приёмы и на каждом
берёт заголовок `["Лечение кариеса", "Профессиональная гигиена", "Лечение пульпита", "Установка
коронки"][index % 4]`, цену `[7200, 5400, 14800, 26500][index % 4]`, скидку
`index % 5 === 0 ? 800 : 0`, статус жёстко `"completed"`, `ORG_ID =
d0000000-0000-4000-8000-00000000d001`. При 10 завершённых приёмах это даёт ровно:

| Ожидание из кода сеялки | Живая база (`group by title`) |
|---|---|
| Лечение кариеса ×3 по 7200, из них 1 со скидкой 800 (index 0) | Лечение кариеса ×3, 7200.00, disc800 = 1 |
| Профессиональная гигиена ×3 по 5400, из них 1 со скидкой 800 (index 5) | Профессиональная гигиена ×3, 5400.00, disc800 = 1 |
| Лечение пульпита ×2 по 14800, скидок нет | Лечение пульпита ×2, 14800.00, disc800 = 0 |
| Установка коронки ×2 по 26500, скидок нет | Установка коронки ×2, 26500.00, disc800 = 0 |
| статус только `completed`, `visit_id` заполнен всегда, `service_id` заполнен всегда, `tooth_code` не заполняется никогда | statuses = 1 (`completed`), with_visit = 10, with_service = 10, no_tooth = 10 |

Совпало всё, включая то, на каких именно двух заголовках стоит скидка. Другого источника у этих
строк нет: `migrateStateToDb.ts` их только удаляет, боевые маршруты не вставляют.

**Что из этого следует для ответа на главный вопрос.** Живые 10 строк — это не «фактически
выполненное, накопленное клиникой», а разовый снимок демо-данных, у которого автор поставил
статус `completed` затем, чтобы отчёты показали деньги. Пустота `treatment_plans` (0 строк)
объясняется тем же: сеялка планов не создаёт. То есть сегодняшняя картина «10 против 0» не
описывает никакого замысла разделения таблиц — она описывает отсутствие писателя у одной и
демо-заполнение другой.

**Побочная находка, не моя к исправлению, но названная числом.** Сеялка пишет цены из своего
жёсткого массива целых чисел, а не из прайса, который создаёт сама же на 30 строк выше:
в `service_catalog_items` лежит `T01 Лечение кариеса 7200.50` и `T02 Лечение пульпита 14800.99`,
а в `treatment_items` у тех же услуг `7200.00` и `14800.00`. То есть демо-данные теряют
`0.50 × 3 + 0.99 × 2 = 3.48 ₽` уже на входе, и любой прогон, сверяющий позицию лечения с
прайсом, найдёт расхождение, которого нет в коде маршрутов.

## 5. Вердикт: две сущности, и вот проверяемые признаки

Сущность одна и та же — тогда, когда у двух таблиц совпадает ключ, совпадает жизненный цикл и
совпадают потребители. Здесь не совпадает ни одно из трёх:

1. **Ключ разный.** У `treatment_items` строка принадлежит ПАЦИЕНТУ (`patient_id not null`) и
   живёт, пока живёт пациент. У `treatment_plan_items_new` строка принадлежит ДОКУМЕНТУ
   (`plan_id not null`, пациента у строки нет) и умирает вместе с перезаписью плана — маршрут
   удаляет все позиции плана и вставляет заново (`odontogram.ts:446`, `:468`).
2. **Жизненный цикл разный.** У позиции книги лечения он есть и им пользуются: `diary.ts`
   переводит в `completed` при закрытии приёма. У позиции сметы его нет вообще — колонки
   `status` в таблице не существует, отменить одну услугу в смете нечем.
3. **Потребители не пересекаются ни в одной точке.** Деньги (8 читателей) читают только
   `treatment_items`. Этапность и recall (2 читателя) читают только
   `treatment_plan_items_new`. Ни одного общего читателя нет.

Плюс признак от документа: у `treatment_plans` есть `patient_signature`, `version`, `approved_at`
и запрет правки подписанного плана (`odontogram.ts:419-425`). Это артефакт, который пациент
подписывает. Бухгалтерская книга подписи не имеет и иметь не должна: в неё дописывают.

**Формулировка сущностей, годная для следующего инженера:**

* `treatment_plans` + `treatment_plan_items_new` — **СМЕТА-ДОКУМЕНТ**: что пациенту предложили,
  разложенное по этапам, с его подписью. Версионируется, перезаписывается целиком, замораживается
  подписью.
* `treatment_items` — **КНИГА ЛЕЧЕНИЯ ПАЦИЕНТА**: обязательства пациента заплатить, каждое со
  своим статусом от `proposed` до `completed`. Единственный источник денег для всей клиники.

Отношение между ними — не «копия», а «документ и его проводка». Смета без проводки — это
бумага, которую никто не считает; ровно это и наблюдается: план на 3 491,49 ₽ сохранён, а
клиника видит долг 0 ₽.

## 6. Почему чинить писателя, а не читателей — семь причин, каждая проверяемая

Второй вариант из постановки («деньги читают не ту таблицу, чинить читателей») отвергнут не по
вкусу, а потому что `treatment_plan_items_new` физически не может ответить на денежные вопросы:

1. **Нет `patient_id`.** Дебиторка группируется по пациенту (`managerReports.ts:1125`). Пришлось
   бы join через `treatment_plans`, а `organization_id` там тоже нуллябельна.
2. **`organization_id` нуллябельна и маршрутом не заполняется.** Каждый денежный читатель
   фильтрует по организации; строки без организации выпали бы из отчётов молча — это не ошибка,
   а тишина, худший исход для денег.
3. **Нет `status`.** Все девять расчётов долга начинаются с `status <> 'cancelled'`. Отменённая
   услуга продолжала бы висеть долгом.
4. **`price` и `discount` объявлены в `schema.ts` БЕЗ `mode: "number"`.** Drizzle отдаёт такие
   `numeric` строкой, и предупреждение об этом стоит в самом `schema.ts` рядом с
   `treatment_items.price_rub`: «арифметика над суммой склеит строки вместо сложения». Маршрут
   уже вынужден прогонять их через `numeric()`-обёртку (`odontogram.ts:130-133`,
   `Number(value ?? 0)` с тихим нулём при отказе). Строить деньги клиники на колонке, которая
   приходит строкой и разбирается функцией с тихим нулём, нельзя.
5. **`quantity` целочисленная.** У `treatment_items` она `numeric(10,2)`; перенос читателей
   сузил бы модель данных.
6. **Нет `visit_id`.** Сумма счёта фильтрует позиции по визиту (`guards.ts:1085`), закрытие
   приёма ищет позиции по визиту (`diary.ts:279`). Оба сломались бы.
7. **Цена правки.** Писатель один файл (`routes/odontogram.ts`). Читатели — восемь файлов, из
   которых `managerReports.ts`, `reports.ts`, `billing.ts`, `guards.ts` в этот момент правят
   другие агенты. Одинаковый результат при восьмикратном риске — это не выбор.

## 7. Приговор лишней таблице: лишней нет

Ни `treatment_items`, ни `treatment_plan_items_new` не подлежат удалению.

* `treatment_items` — единственный источник денег, восемь читателей.
* `treatment_plan_items_new` — единственный носитель этапности (`phase`) и группировки по
  подписываемому плану; два живых читателя (`recallScheduler.ts`, `toothHistory.ts`), которых
  на `treatment_items` не перевести без миграции, потому что колонки `phase` там нет.

Приговор выносится другому — **имени `treatment_plan_items_new`**. Суффикс `_new` означает, что
когда-то существовала таблица `treatment_plan_items`, и он уже стоил этому дереву дорого:
таблица «позиции плана лечения» (`treatment_items`) и таблица «позиции плана лечения новые»
(`treatment_plan_items_new`) читаются как одна сущность в двух версиях, чем они не являются.
Переименование — миграция, и она не моя. Но пока имя такое, каждый следующий агент будет
проходить ту же развилку, что и я в разделе 0.

Отдельно, к сведению, а не к исправлению в этом заходе:

* `treatment_items.price_rub` **не читает никто** (проверено `rg` по всему `apps/api/src` и

  `tests/routes/serviceCatalogWriteProof.ts:194` так и называет проверку — «вторая денежная
  колонка заполнена тем же (price_rub)». Ей и следую.
* `treatment_plan_items_new.commission_amount` `not null default 0` в живой базе и **не объявлена
  в `schema.ts`** вовсе.

## 8. Расхождение `schema.ts` с живой базой — ловушка для следующего

`schema.ts` читать как истину нельзя, и это измерено, а не предположено:

| Объект | В `schema.ts` | В живой базе |
|---|---|---|
| `treatment_items` | 15 колонок | **17**: сверх объявленных `is_synced`, `version` |
| `treatment_plan_items_new` | 11 колонок | **12**: сверх объявленных `commission_amount` |
| `treatment_plan_items_new.price_id` | `.notNull()` | **nullable** |
| `treatment_plan_items_new.price`, `.discount` | `numeric(10,2)` | `numeric(12,2)` |
| `treatment_plans.status` | `text().default("draft")` | перечисление `treatment_plan_status` со значениями **`Draft`, `Active`, `Approved`, `Completed`, `Rejected`** — с большой буквы, и `"draft"` из `schema.ts` в нём отсутствует |

Последняя строка — заряженное ружьё: любая попытка задать статус плана строкой `"draft"` из
кода получит от PostgreSQL отказ по перечислению. Сегодня это не стреляет только потому, что
маршрут статус не задаёт и работает значение по умолчанию самой колонки.

Проверять форму таблицы надо запросом к `information_schema`, а не чтением `schema.ts`.
