# CTO Audit & Architectural Documentation: Financial & Billing Engine

> [!WARNING]
> **ARCHITECTURAL DISCREPANCY DETECTED**
> The premises provided in the task prompt contained systemic inaccuracies regarding the codebase state. This report corrects those assumptions based on factual AST and database schema analysis (verified 2026-08-11).

## 1. Codebase Reality Check: Routing & Ledger Entities

The requested focus areas do not exist as described:
- **`apps/api/src/routes/payments` DOES NOT EXIST.** Payment logic is localized in `apps/api/src/routes/billing.ts` and `apps/api/src/db/billingQuery.ts`.
- **`apps/api/src/routes/treatment-plans` DOES NOT EXIST.** Treatment item creation and processing are handled via `apps/api/src/routes/odontogram.ts` (as identified in `schema.ts` comments).
- **`cash_ledger` DOES NOT EXIST.** There is no dedicated cash ledger table or logic. The system uses a flat `payments` table and derives financial state via aggregation.

## 2. The "Kopecks as Integers" Myth

> [!IMPORTANT]
> **Kopecks are NOT stored as integers in the database.**

Historical analysis of `apps/api/src/db/schema.ts` reveals this was a legacy constraint that broke the cash register (it rejected legitimate inputs like 1500.50 ₽).
- **Migration 0131** permanently eradicated integer storage for payments.
- `payments.amountRub`, `family_groups.balance`, and `treatment_items.priceRub` are all strictly typed as `numeric(12, 2)` with drizzle's `mode: "number"`.
- **Integer Math in Memory:** The only place where integer Kopeck processing remains is during in-memory calculation for Family Wallets (`apps/api/src/routes/finance_family.ts`). The system uses `parseKopecks()` to convert the `numeric` string to an integer to avoid floating-point drift during subtraction (`currentKopecks - amountKopecks`), and then uses `kopecksToNumericString()` to format it back for database insertion.

## 3. Cash Shifts & Payout Slicing

**Cash shifts are not explicitly "closed".** There is no entity tracking an open/closed register.
- **The Mechanism:** Revenue and doctor payouts are purely query-based, sliced by the `payments.paidAt` timestamp.
- **The Defect (Documented in `billingQuery.ts`):** `paidAt` is generated by `defaultNow()` (the exact moment the button is pressed). The API does not accept a custom `paidAt` date from the client.
- **The Business Impact:** Because cash shifts are inferred via timezone boundary resolution (`clinicTimeZone` in `billing.ts`), a cashier logging yesterday's cash this morning will permanently attribute that money to today's shift. This corrupts doctor payouts and tax deduction periods. 

## 4. Advance Deposits & Installments

### Advance Deposits (Family Wallets)
Advance deposits do not exist as a standalone accounting primitive. They are implemented entirely through **Family Wallets** (`family_groups` table).
- **Top-ups:** Handled via `POST /api/finance/family/topup`. The balance is increased.
- **Deductions:** `POST /api/finance/family/pay` deducts the balance and generates a corresponding `payments` record with `method: "family_wallet"`.
- **Safety:** Both endpoints utilize PostgreSQL row-level locks (`.for("update")`) and `clientMutationId` to guarantee idempotency and prevent double-billing on network retries.

### Installments (Рассрочка)
Installments are not tracked in a dedicated ledger schedule. They are implemented purely as a legal document type (`documentKind: "installment_payment_schedule"`) in the `generated_documents` table.

## 5. Payment Idempotency Engine

To prevent duplicate charges, DENTE uses a strict validation layer:
1. `POST /api/billing/payments` receives a payload with a `clientMutationId`.
2. The server queries `findPaymentByClientMutationIdInDb`.
3. If a collision is found, the server validates the incoming payload against the existing record using `paymentRetryMatchesExisting()` (checking amount, method, patient, and receipt details).
4. If they match identically, it safely resolves with `200 OK`. If they mismatch, it rejects with `409 Conflict`.
5. At the database level, the `payments_org_client_mutation_unique` constraint acts as the final hard barrier.
