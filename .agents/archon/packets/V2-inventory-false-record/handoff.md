## Долг

**1. `routes/inventory.ts:410-417` обязан писать `organization_id`, а колонке нужен NOT
NULL с бэкфиллом. НЕ МОЙ ФАЙЛ — нужен пакет ведущему.** Правка на одну строку:

```ts
const [newRule] = await db.insert(procedureMaterialRules).values({
	organizationId,          // <- этой строки нет
	serviceId,
	inventoryItemId,
	quantityToDeduct: String(Math.max(1, quantityToDeduct)),
}).returning();
```

Пока её нет, продукт продолжает создавать ничьи правила; мой `IS NULL` их обслуживает, но
это терпимость к неверным данным, а не порядок. После правки — бэкфилл
`update procedure_material_rules r set organization_id = i.organization_id from
inventory_items i where i.id = r.inventory_item_id and r.organization_id is null`, затем
`alter column set not null`. Тогда `IS NULL` из `diary.ts` можно будет убрать.

**2. Там же (`inventory.ts:403` и `:415`) `String(Math.max(1, quantityToDeduct))` молча
превращает 0 и отрицательное в 1.** Это и есть настоящее «0 становится 1» в этом
репозитории — на записи, а не на чтении, и оно на месте. Врач просит «не списывать» —
получает списание 1. Нужен явный отказ 400, а не подмена значения.

**3. CHECK-ограничения на количества (то, о чём просил пакет; здесь — предложение, не
миграция; `schema.ts` я не трогал).** На трёх таблицах нет ни одного CHECK, поэтому
отрицательное количество база принимает, и защита живёт только в коде маршрута:

```sql
ALTER TABLE procedure_material_rules
  ADD CONSTRAINT procedure_material_rules_quantity_to_deduct_positive
  CHECK (quantity_to_deduct > 0);
ALTER TABLE treatment_items
  ADD CONSTRAINT treatment_items_quantity_positive
  CHECK (quantity > 0);
ALTER TABLE inventory_items
  ADD CONSTRAINT inventory_items_stock_quantity_non_negative
  CHECK (stock_quantity >= 0);
```

Первые два — строго положительные: «услуга в количестве 0» и «правило, списывающее 0» не
имеют смысла ни в одном сценарии клиники. Третье — неотрицательное: нулевой остаток
законен, отрицательный — нет. Перед применением: `select count(*) from
procedure_material_rules where quantity_to_deduct <= 0` и то же по двум другим таблицам —
сейчас все три дают 0, так что ограничения встанут без бэкфилла. `inventory_items`
дополнительно защитит от ошибки в любом будущем маршруте, а не только в церемонии.

**4. Расхождение схемы с базой (три колонки integer против numeric) — миграция.**
Следствие измерено в §8.2 выше: подписание приёма с дробным количеством падает в 500.

**5. Две колонки под один остаток (`stock_quantity` / `current_qty`).** После удаления
фолбэка `current_qty` не читает НИКТО во всём API, а пишет её только миграция. Либо
удалить колонку, либо решить, что она значит. В `schema.ts` она объявлена `.notNull()`,
а в живой базе `nullable=YES` — ещё одно расхождение модели с базой.

**6. `diaryDeductionProof.ts` оставлен на диске намеренно** — воспроизводимый замер.
Лежит в `src/tests/`, поэтому не попадает ни в `npm test` (имя без `.test.ts`), ни в
`tsc` (`tsconfig.json` исключает `src/tests`); последнее значит, что его типы не
проверяются — как и у всех тестов этого репозитория. Пишет в живую базу и убирает за
собой.
