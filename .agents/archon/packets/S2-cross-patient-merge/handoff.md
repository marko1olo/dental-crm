## Что изменено

Один файл: `apps/api/src/speech/storage.ts` (плюс новый тест). Строки — по текущему HEAD.

1. `storage.ts:742-754` `persistSpeechRecording` принимает сам фрагмент, а не только `recordingId`,
   и ВНУТРИ очереди записи по `recordingId` сверяет его личность с сохранённым конвертом — с тем же
   чтением (`loadDurableRecordingEnvelope`), которое использует слияние. Владелец записи — фрагмент

   (409) до любой записи. Вытеснение обойти эту проверку не может: конверт в базе не вытесняется.

   владелец конверта, иначе сам фрагмент). Поэтому смешанный документ не собирается даже при
   одновременных запросах: очередь записи по `recordingId` последовательна, второй запрос увидит
   конверт первого.
3. `storage.ts:684-703` `forgetCachedSpeechChunk` — отклонённый фрагмент убирается из горячего кэша.
   Оставленный там, он не попал бы ни в одну строку, зато вытеснение выбросило бы его МОЛЧА: ключ

   пометило бы чужой как «подтверждённо сохранённый». `durableChunkKeys` намеренно не трогается — ключ
   может принадлежать законному фрагменту.
4. `storage.ts:1152-1157` `withDurableSpeechRecording` пропускает наверх именно эту ошибку, а не
   превращает её в предупреждение «сохранено, но…». Иначе клиент счёл бы фрагмент принятым и удалил бы
   его из локальной очереди. Роут `apps/api/src/routes/speech.ts:291-292` отдаёт 409 `chunk_conflict`.
5. `storage.ts:1076-1090` проверка по кэшу оставлена как быстрый отказ до похода в базу и выражена той
   же функцией `speechRecordingIdentityMatches`. Отдельная проверка фрагмента с тем же номером

6. `storage.ts:757` + `:785-788` уже смешанные конверты (следствие прежнего дефекта) НЕ чистятся — уничтожать

## НЕ ПРОВЕРЕНО

1. **API VERIFIED не заявляется.** Живой HTTP-отказ 409 через работающий сервер на 4100 я не прогонял:
   чтобы воспроизвести холодный кэш на общем сервере, нужно вытеснить запись 80 посторонними записями,
   а сервер общий и его нельзя перезапускать. Закрывающая команда (после того, как процесс подхватит
   этот код, и на своей, не общей копии):
   `curl -s -o - -w "\n%{http_code}\n" -X POST http://127.0.0.1:4100/api/speech/transcribe-chunk -H "content-type: application/json" -H "x-dente-clinic-token: <signToken({organizationId}, TOKEN_SECRET())>" -d '{"recordingId":"<та же>","chunkIndex":1,"visitId":"<чужой прием>","patientId":"<чужой пациент>","source":"visit","language":"ru","mimeType":"audio/webm","localTranscript":"проверка"}'`
   — ожидается 409 и `"reason":"chunk_conflict"`.
2. **Поведение клиента на 409 прочитано в коде, но не проиграно в браузере.** Очередь распознавания
   прерывается на первом отказе (`useVisitLogic.ts:881-889`: `for` по очереди, `await submitSpeechChunk`
   бросает — цикл прекращается), поэтому неустранимый 409 в голове очереди задержит отправку
   ПОСЛЕДУЮЩИХ фрагментов той же очереди до вмешательства. Это свойство было и раньше для любого 409;
   моя правка делает 409 достижимым ещё в одном состоянии (запись вытеснена из кэша). Закрывающая
   проверка — в вебе, вне моей делянки: `UI VERIFIED` лида либо тест на очередь IndexedDB.
3. **Межпроцессная гонка мной не прогонялась.** Проверка личности защищает от одновременных запросов
   В ОДНОМ процессе (очередь по `recordingId`), и это проверено тестом. Два процесса API по одной базе
   могут прочитать пустой конверт одновременно. Уточнение по факту, а не по памяти: пакет S3 УЖЕ
   закоммитил и применил уникальный индекс — в живой базе есть
   `CREATE UNIQUE INDEX ai_jobs_organization_storage_path_key ON public.ai_jobs USING btree (organization_id, input_storage_path)`
   (прочитано в `pg_indexes` на 127.0.0.1:5432), миграция `apps/api/drizzle/0134_ai_jobs_recording_path_index.sql`.
   Поэтому форма «два процесса создали две строки на одну запись» закрыта на уровне базы: второй
   INSERT падает на уникальности, `withDurableSpeechRecording` вешает явное предупреждение и строку не
   портит. Чего я НЕ прогонял: интерливинг, в котором процесс А вставляет строку между чтением
   конверта процессом Б и его INSERT. Закрывающая команда: два процесса node, каждый вызывает
   `recordSpeechTranscriptionChunk` на одну `recordingId` с разными приемами, синхронизированные по
   времени; ожидается одна строка одного приема и явное предупреждение у второго процесса.
4. **Смешанные строки, созданные прежним дефектом, не разделяются.** Код их не уничтожает и помечает
   предупреждением, это проверено тестом. Разделить текст двух приемов на две строки автоматически —
   значит угадывать, чей абзац; это должен делать человек. Найти такие строки:
   `SELECT id, organization_id, visit_id, patient_id FROM ai_jobs WHERE kind = 'voice_transcription' AND input_storage_path LIKE 'speech-recording://%';`
   и сравнить `visitId` фрагментов внутри `input_text`. В этой установке их сейчас нет (0).
5. **Одно последствие смешанного конверта, которое я не устранял:** после перезапуска процесса
   восстановление поднимает в память ВСЕ фрагменты такой строки, включая чужой, и тогда быстрый отказ
   по кэшу начинает отклонять фрагменты ОБОИХ приемов, пока запись не вытеснится. Для отравленной
   записи это защита, а не регресс, но заявляю прямо: диктовка по такой `recordingId` не продолжится,
   пока строку не разберут вручную. Проверяется тем же тестом наоборот — без вытеснения кэша.
