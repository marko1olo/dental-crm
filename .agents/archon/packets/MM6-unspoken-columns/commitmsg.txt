[ARCHON] fix(схема): деньги, права подписи и согласие пациента лежали в базе колонками, о которых Drizzle не знает

В живой базе 134 колонки в 34 объявленных таблицах не имели объявления в
apps/api/src/db/schema.ts. Скрипт паритета этот класс не считает ошибкой по
своему же заголовку, поэтому колонки жили незамеченными с миграции 0000.
Объявлены пять худших — «худшая» выбрана по вреду, подтверждённому живым
потребителем в коде, а не по алфавиту.

1. patient_invoices.total_amount_rub — numeric(12,2) DEFAULT '0' NOT NULL,
   миграция 0000, строка 841. В исходной схеме это ЕДИНСТВЕННАЯ сумма счёта:
   total_rub в 0000 отсутствует, его дописала в базу миграция 0118
   «выравнивание таблиц по схеме» — под уже написанное объявление. Выравнивание
   пошло не в ту сторону: вместо объявления живой колонки в базе появился
   денежный дубль. Итог на деньгах: apps/api/src/scripts/cronAnalyticsWorker.ts
   складывает сырым SQL именно total_amount_rub (выручка когорт LTV и выручка по
   врачам), а всё, что пишет счёт через drizzle, заполняет total_rub. Колонка
   остаётся на своём DEFAULT 0 — оба отчёта суммируют нули.

2. users.can_manage_money и
3. users.can_sign_medical_records — boolean DEFAULT false NOT NULL, миграция
   0000, строки 1078-1079. База хранит эти права пофамильно, но прочитать их
   было нечем, и потребители подставляли своё: settingsQuery.ts отдаёт КАЖДОМУ
   сотруднику canManageMoney: true и canSignMedicalRecords: true константой,
   domainStateHydration.ts выводит те же права из роли. Право распоряжаться
   деньгами и право подписывать медицинские записи выдавались догадкой.

4. egisz_blank_permissions.patient_opt_out_respect — boolean DEFAULT true NOT
   NULL, миграция 0103, строка 7. Это согласие: флаг решает, будет ли учтён
   отказ пациента при выгрузке его медицинских данных в государственный реестр.
   Виджет EgiszBlankPermissionsWidget.tsx уже показывает его словами
   «учитывается» / «не учитывается», серверного маршрута к таблице нет ни
   одного, а через drizzle колонка недостижима.

5. crm_leads.expected_revenue — numeric(12,2), миграция 0000, строка 293.
   POST /api/leads принимает expectedRevenue в схеме разбора и пишет лид через
   values({ ...data, organizationId }): ключа, которого нет в форме таблицы,
   drizzle в запрос не переносит, а GET /api/leads читает те же объявления.
   Сумма, введённая администратором, не доходила до базы, и канбан лидов
   показывал поле, которое нечем заполнить.

Миграций не добавлено и не требуется: все пять колонок в базе уже есть, добавлены
только объявления. Тип каждой сверен с information_schema.columns живой базы —
тип, nullable и default, а не догадка. total_amount_rub объявлен с mode: "number",
потому что registerMoneyTypeParsers() ставит разбор numeric на весь процесс и
драйвер отдаёт число; expected_revenue — без mode, потому что маршрут разбирает
это поле как z.string(). notNull-колонки объявлены с .default(), иначе drizzle
потребовал бы поле в каждом insert в users.

В реестре исключений стража снято ровно пять записей (у crm_leads запись была
одноколоночной и удалена целиком) — иначе устаревшая запись валит прогон, как и
задумано автором стража.

ЧЕГО ЗАМЕР НЕ ПОДТВЕРДИЛ. Ни одна из 134 колонок не является NOT NULL без
значения по умолчанию: NOT NULL их 81, и у всех 81 есть DEFAULT. Ни одна вставка
через drizzle из-за этих колонок упасть не могла и не падала. В ограничениях
участвует РОВНО ОДНА колонка из 134 — patients.insurance_contract_id, внешний
ключ на insurance_contracts.id; уникальных ограничений нет ни у одной. Данных за
незаявленными колонками сегодня тоже нет: patient_invoices, crm_leads и
egisz_blank_permissions пусты, у 7 пользователей оба права false, у 17 пациентов
номер полиса не заполнен. Вред здесь структурный и наступит на первой же реальной
записи, а не уже случившаяся потеря.
