## FOUND

### 1. РЕГРЕСС: отзыв привязки больше не останавливает отправку. Замерено пробником
Постоянный текст `954111dcc` и комментарий в `routes/telegram.ts:2930` утверждают: «отзыв
снимает привязку в **обоих** хранилищах — иначе клиника отключила бы чат, а очередь продолжила
в него писать». Ровно это и происходит.

Механизм: `dente_telegram_chat_links.id` — `uuid().primaryKey().defaultRandom()`
(`db/schema.ts:818`), значение рождает Postgres. Связка в памяти получает `id: randomUUID()`
(`sampleData.ts:6316`). `upsertDenteTelegramChatLink` идентификатор из памяти НЕ переносит.
Маршрут отзыва передаёт `request.params.linkId` (теперь это идентификатор ИЗ БАЗЫ, потому что
список теперь из базы) в `revokeLegacyInMemoryTelegramChatLink`, а тот ищет `link.id === linkId`
(`sampleData.ts:6493`) — и не находит.

Пробник (`node --import tsx`, боевые маршруты, живая база; файл удалён после замера):
```
LINK_CODE_HTTP  = 200
MEMORY_LINK_ID  = e53d6c0b-6363-436c-949b-67a3f14d8614
DB_ROW_ID       = d99027f3-528d-44b2-9056-e6d3ce1aa24f
IDS_EQUAL       = false
MEMORY_STATUS_BEFORE = active      DB_STATUS_BEFORE = active
REVOKE_HTTP     = 200
MEMORY_STATUS_AFTER = active       DB_STATUS_AFTER  = revoked
QUEUE_STILL_SEES_ACTIVE_LINK = true
```
Цена. Отправляет именно память: `prepareDenteTelegramOutboxDelivery` (`sampleData.ts:9907`)
ищет связку в массиве по `item.chatLinkId`, требует `status === "active"` и берёт оттуда
`chatTransportRef` для расшифровки адреса чата. Значит после отзыва очередь продолжает писать
пациенту, который привязку отозвал. Это не «недоделанная миграция», это отзыв согласия на
переписку, отвечающий 200 и ничего не отзывающий.

Хуже двух деталей:
* **до пакета отзыв РАБОТАЛ.** Список шёл из памяти → панель показывала идентификаторы памяти →
  `link.id === linkId` совпадал. Пакет поменял источник идентификаторов и оставил старый поиск.
* **расхождение переживает перезапуск.** Провалившийся синхронный отзыв выходит по `if (!chatLink)
  return null` ДО `persistMutableState()` (`sampleData.ts:6499-6503`), поэтому в файле состояния
  связка тоже остаётся активной. Восстановления нет: `hydrateDomainStateFromDb` связки чатов не
  трогает вообще (`rg -n "chatLink" apps/api/src/db/domainStateHydration.ts` — 0 вхождений), так
  что память из базы не подтягивается никогда.

Тест этого не видит: третий тест проверяет только строку в базе. Стража на «в памяти тоже
снято» нет — а именно на этой связке держится вся конструкция «две реализации, обе живые».

Починка мелкая: снимать копию в памяти не по идентификатору базы, а по тому, что у двух
хранилищ общее — `(organizationId, botConfigId, chatFingerprint)` или `subjectId`; и добить
тестом, что после отзыва массив процесса не содержит активной связки этого пациента.

### 3. Ловушка внешнего ключа не просто обойдена — она СТЁРТА, без единой записи в журнал
`persistableClinicId` (`chatLinks.ts:176`) проверяет наличие филиала и при отсутствии молча

### 4. Панель теперь мешает честное число с выдуманным нулём, в соседних строках

Снятие `isPrimaryRuntime` со второй строки обосновано и правильно. Но первая осталась: вторая

### 5. `fail 1` в постоянном тексте `577c41f6b` не воспроизводится: реально `fail 3`
Причина не только в счёте, она структурная. Четвёртый тест удаляет свою вторую связку последней
строкой ТЕЛА теста, а не в `afterEach`/`finally`. Когда он падает (а при порче №1 он падает,
потому что читает тот же маршрут), строка остаётся в базе и роняет шестой тест сообщением
«своя клиника видит 2 связок вместо одной» — чужим для этой порчи. Итог: одна порча даёт три
отказа, из которых один — эхо утечки фикстуры. Числу в постоянном тексте это цену снижает, а
диагностике будущих отказов — тем более. `before()` подчищает организацию целиком, так что
следующий прогон зелёный, — поэтому и не заметили.

### 6. Мелкое: страница считается двумя отдельными запросами без снимка
`buildDenteTelegramChatLinkList` берёт `filteredCount` одним `count(*)`, строки — вторым
`select … limit/offset`, транзакции нет. Параллельная вставка между ними даёт `nextCursor`,
рассчитанный от одного набора, и страницу от другого — пропуск или дубль. На версии в памяти
этого не было (один массив), так что формально это новый, хоть и малый, риск. Устойчивый
`orderBy(lastUpdateAt desc, id desc)` — правильное решение, его как раз проверяет четвёртый тест.
