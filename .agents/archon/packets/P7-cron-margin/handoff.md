## Есть ли настоящая себестоимость: ответ — НЕТ (это главная находка)

Пакет требовал искать, а не предполагать. Схема такие таблицы содержит:
`inventory_transactions.unit_cost_rub` (+ `visit_id` — фактический расход на приём),
`inventory_items.unit_cost_rub`, `procedure_material_rules`,
`doctor_commissions.material_cost_deduction_pct`,
`pricelist_doctor_payrolls.doctor_payroll_rub` / `clinic_margin_rub`.

Все они **пусты**. Перепись только на чтение против 127.0.0.1:5432
(`.agents/archon/packets/P7-cron-margin/cost-data-census.cjs`):

```
       0   inventory_transactions       actual material movements (unit_cost_rub, visit_id)
       0   inventory_items              material catalogue
       0   procedure_material_rules     planned material per procedure
       0   doctor_commissions           per-doctor labour rate
       0   pricelist_doctor_payrolls    per-service payroll + clinic margin
       8   payments                     paid revenue rows (the numerator)
```

Вывод: **вариант (a) «посчитать маржу честно» невозможен**. Пустая таблица затрат дала бы
себестоимость 0, то есть «вся выручка — прибыль»: ложь крупнее прежних 40 %. Пакет прямо
запрещает подставлять 0 вместо неизвестного.

**А вот данные об успешности — есть.**
(`.agents/archon/packets/P7-cron-margin/schema-reality-check.cjs`):

```
  appointments total                   27
  appointments completed               13
  appointments with doctor             27
  статусы: completed 13, planned 5, cancelled 4, no_show 3, confirmed 2
```

Поэтому `completionRate` обязан считаться, а не зануляться — ровно как требовал пакет
(«if the underlying completion data IS available, compute it for real»).

## Выбран вариант (b), с настоящим расчётом успешности

- `margin` → **null** всегда. Себестоимости нет; 0 запрещён.
- `completionRate` → **реальная доля завершённых приёмов врача в процентных пунктах**,
  `null` когда приёмов нет вовсе.

**Почему не (c) «удалить файл».** Три из четырёх агрегатов в нём — честные запросы к
реальным таблицам, и методически они **лучше**, чем у соседа `services/biAnalyticsWorker.ts`
(тот выдумывает LTV множителями `*1.5 / *2 / *3`, добивает воронку через `|| 1` и
подставляет демо-кресла `{Chair 1: 10, Chair 2: 5}`). Удаление уничтожило бы честную работу
и при этом **не убрало** бы худшую выдумку соседа. Файл сохранён не «чтобы что-то изменить»,
а потому что три его секции считают настоящие числа.

**Единица измерения — важная ловушка, в которую легко было упасть.**
`formatCompletionRate` (`analyticsDoctorMetrics.ts:117-118`) ждёт **процентные пункты**
(85 = 85 %), а `services/reports/managerReports.ts:255` отдаёт **долю 0..1**. Это разные
контракты; доля 0.53 отрисовалась бы как «1 %». Взят контракт потребителя снимка.

   отсутствии приёмов.
3. Запрос переписан на два CTE: `doctor_revenue` и `doctor_appointments`.
   **Зачем:** выручка идёт внутренним соединением через оплаченные счета
   (`appointments → visits → patient_invoices`), и это множество завершённое по
   построению — успешность на нём вышла бы около 100 % у любого врача. Успешность
   считается по всему приёмному журналу.
4. **Соединения стали внешними — это осознанное изменение поведения.** Раньше врач попадал
   в срез только при наличии оплаченного счёта; врач с приёмами, но без счетов, исчезал
   вместе со своей измеримой успешностью. Ноль в выручке у такого врача — не выдумка:
   оплаченных счетов у него действительно нет.
