[ARCHON] chore(гигиена): файл с именем NUL закрыт от коммита — он ломает поиск и несёт адрес сервера

В apps/api лежал НЕОТСЛЕЖИВАЕМЫЙ файл с именем NUL, 94 байта, создан 28 июля. Внутри — строка вида
known_hosts: вывод ssh-keyscan, то есть ПУБЛИЧНЫЙ ключ хоста и адрес сервера.

ЧТО ЭТО И ЧТО НЕТ. Ключ хоста секретом не является по устройству SSH — known_hosts на то и придуман,
чтобы такие ключи были публичными. Утечки закрытого ключа нет. Но адрес сервера, к которому с этой машины
ходят по SSH, в публичном репозитории лежать не должен, а файл был в одном `git add -A` от публикации:
до этой правки git check-ignore по нему не давал ничего.

ОТКУДА ОН ВЗЯЛСЯ. `команда > NUL` в cmd.exe выбрасывает вывод в устройство-пустышку. В Git Bash на этой
машине NUL устройством не является, и та же строка СОЗДАЁТ ФАЙЛ с перенаправленным выводом внутри.
В отслеживаемых исходниках такой записи нет (git grep по «> NUL» пуст) — значит след ручной команды.

ПОЧЕМУ ЭТО НЕ КОСМЕТИКА. NUL — зарезервированное имя устройства Windows, поэтому файл с таким именем
ломает обход: rg спотыкается на нём с «os error 1» при КАЖДОМ проходе по apps/api, а Win32 API не может
открыть его по имени вовсе (.NET отвечает «получен дескриптор устройства, а не файла»). Прочитать
содержимое удалось только через MSYS-путь. Поиск rg — единственный санкционированный инструмент разведки
в этой кампании, и посторонняя ошибка в его выводе маскирует настоящие ошибки обхода.

ПРОВЕРЕНО, ЧТО ПОТЕРИ ДАННЫХ НЕТ: rg печатает ошибку по этому пути и обход ПРОДОЛЖАЕТ — контрольный
прогон по apps/api/src нашёл совпадения в 227 файлах. То есть это шум, а не молчаливое недоописание,
и заявлять второе было бы преувеличением.

САМ ФАЙЛ НЕ УДАЛЁН НАМЕРЕННО: создан не мной, содержит чужие данные об инфраструктуре, а решение об
удалении чужого — за владельцем. Правка закрывает только публикацию.
