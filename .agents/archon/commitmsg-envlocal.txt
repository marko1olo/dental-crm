[ARCHON] fix(доступ): .env.local лежал в репозитории и снимал охрану клинических данных при обычном npm start

САМАЯ СЕРЬЁЗНАЯ НАХОДКА ЭТОЙ НОЧИ, И ОНА ИЗМЕРЕНА, А НЕ ВЫВЕДЕНА. Файл .env.local был ОТСЛЕЖИВАЕМЫМ в
git, то есть уезжал в оба удалённых репозитория, и содержал:

    NODE_ENV=development
    DENTE_CLINICAL_ALLOW_UNGUARDED_MUTATIONS=1
    DENTE_CLINICAL_ALLOW_UNGUARDED_READS=1
    DENTE_SETTINGS_ALLOW_UNGUARDED_MUTATIONS=1

А apps/api/src/accessGuard.ts:18 выглядит так:

    return process.env.NODE_ENV !== "production" && process.env.DENTE_CLINICAL_ALLOW_UNGUARDED_MUTATIONS === "1";

То есть охрана клинических данных снимается при выполнении ДВУХ условий, и отслеживаемый файл задавал
ОБА сразу.

ПОЧЕМУ ЭТО РАБОТАЛО БЫ У КЛИНИКИ, А НЕ ТОЛЬКО У РАЗРАБОТЧИКА. apps/api/package.json:8 объявляет
"start": "node dist/server.js" — NODE_ENV там НЕ задаётся. Ни один Dockerfile его тоже не задаёт
(проверено grep по всем Dockerfile). А apps/api/src/env/loadServerEnv.ts:65-69 читает .env.local из корня
репозитория первым в списке базовых файлов. Значит после обычного клонирования и npm start сервер
поднимался с NODE_ENV=development и тремя флагами «разрешить без охраны» — то есть охрана клинических
чтений и записей была СНЯТА по умолчанию.

ЧТО МЕНЯ ОСТАНОВИЛО ОТ ПРЕУВЕЛИЧЕНИЯ. Проверил приоритет: loadServerEnv.ts:59 ставит значение только
если process.env[name] === undefined, то есть файл НЕ перебивает настоящее окружение. Оператор, который
честно выставил NODE_ENV=production, защищён: его значение остаётся, и accessGuard возвращает false.
Уязвим тот, кто NODE_ENV не задал вовсе, — а именно так работает и штатный npm start, и наивный запуск в
контейнере. Формулирую точно: это не дыра в правильно настроенном продакшене, это ВООРУЖЁННАЯ ПО
УМОЛЧАНИЮ дыра в свежем клоне.

ПОЧЕМУ УДАЛЕНИЕ ИЗ УЧЁТА ЗАКРЫВАЕТ ВОПРОС ПОЛНОСТЬЮ, А НЕ ПРЯЧЕТ ЕГО. Без этого файла все три флага
отсутствуют, и сравнение === "1" даёт false независимо от NODE_ENV. То есть охрана держится. Файл при
этом ОСТАЛСЯ НА ДИСКЕ (git rm --cached, не git rm), поэтому локальная разработка не сломалась ни на шаг.

И ЭТОГО ФАЙЛА В УЧЁТЕ НЕ ДОЛЖНО БЫЛО БЫТЬ НИ ПРИ КАКОЙ СЕРЬЁЗНОСТИ. .gitignore исключает его ТРИЖДЫ —
строкой 4 «.env.local», строкой 5 «.env.*» и строкой 47 «.env*». Отслеживаемый файл правилам игнора не
подчиняется, поэтому он ездил в репозиторий мимо трёх заслонов сразу. Добавил его коммит 99bba4e0c
«chore: final cleanups and script removals» — то есть отслеживаемый файл окружения приехал в уборке.
Прецедент кампании соблюдён: так же были сняты с учёта 149 файлов apps/api/dist, тоже перечисленных в
.gitignore и тоже отслеживаемых.

ОТКУДА НАХОДКА. Разведывательный пакет RC2 исследовал непроверенную личность и первым делом ПОПРАВИЛ мой
бриф: я написал, что requireOrganizationId не читает identity.verified, а проверка перенесена выше, в
getRequestIdentity, и её читает unverifiedOrganizationUsable. Зато агент нашёл то, чего в брифе не было:
отбрасывается только ЗАПИСЬ. identity.ts:112-115 для GET/HEAD/OPTIONS возвращает true сразу, поэтому при
включённом флаге заголовочной организации чтение чужой клиники без токена разрешено и на слушающем порту,
а запись отбивается 401 UnverifiedOrganizationCannotMutate.

Живой порт я опросил сам: GET /api/patients с заголовком x-organization-id и без токена отдаёт 401,
потому что DENTE_DEV_ALLOW_HEADER_ORG не задан ни в .env, ни в apps/api/.env, ни в local-secrets/ai.env
(проверено по именам переменных, значения не печатались). То есть путь заголовочной организации сейчас
закрыт, и я не выдаю его за живую дыру. Настоящая дыра оказалась рядом и хуже — в трёх других флагах.

ПОПРАВКА К МОЕМУ ЖЕ БЭКЛОГУ, ПЯТАЯ УСТАРЕВШАЯ ЗАПИСЬ ЗА НОЧЬ. Пункт T2 у меня гласил, что
apply-dev-env.ps1 пишет DENTE_DEV_ALLOW_HEADER_ORG в ТРИ файла окружения. Это больше неверно: скрипт
прямо объявляет «THE HEADER-ORG FLAG IS NO LONGER PART OF THE DEFAULT SET», требует явного ключа
-AllowHeaderOrg и пишет флаг в ОДИН файл. Кто-то это уже укрепил, а мой бэклог продолжал носить старую
версию. Счёт устаревших утверждений за ночь: «4 организации», вердикт «REVERT», countLabel, настройка
зонда, clinic_mode, и вот T2.

ОСТАЁТСЯ ДОЛГОМ, НЕ ЗАКРЫТО ЗДЕСЬ. Условие безопасности сформулировано как NODE_ENV !== "production", то
есть НЕЗАДАННОЕ окружение считается разрешающим. Это перевёрнутая безопасность по умолчанию: правильнее
требовать явного разрешения, а не отсутствия запрета. Сейчас вопрос закрыт отсутствием флагов, но сама
форма условия остаётся ловушкой для следующего, кто заведёт такой флаг. Это отдельный пакет.

ПРОВЕРЕНО: файл снят с учёта и остался на диске; git check-ignore подтверждает, что теперь он
игнорируется правилом .gitignore:47; значения секретов не печатались нигде — из файла выведены только
ИМЕНА переменных и значения трёх логических флагов и NODE_ENV, которые секретами не являются.
НЕ ПРОВЕРЕНО: поведение свежего клона без .env.local под npm start — закрывается запуском
NODE_ENV= node apps/api/dist/server.js в пустом окружении и проверкой, что клинический маршрут отдаёт 401.
