Последний живой экземпляр анти-паттерна, который три соседних файла описывают как УЖЕ ИСПРАВЛЕННЫЙ дефект.

БЫЛО, apps/api/src/routes/communications.ts:22 —
  const [org] = await db.select().from(organizations).limit(1);
то есть SELECT * FROM organizations LIMIT 1. Организация не выводилась из звонящего ВООБЩЕ, ни при каком
значении секрета периметра.

ПОСЛЕДСТВИЯ ПРИ НЕСКОЛЬКИХ КЛИНИКАХ В ОДНОЙ БАЗЕ:
  • задача связи закрывалась в ПЕРВОЙ организации таблицы независимо от того, чья клиника её закрывает;
  • строка в communicationEvents писалась с organizationId первой организации — в историю коммуникаций
    ЧУЖОЙ клиники;
  • клиника, не являющаяся первой строкой, не могла закрыть даже свою задачу: фильтр по organizationId
    был прибит к организации №1.

ЭТО НЕ НОВЫЙ КЛАСС. Тот же анти-паттерн уже стоил денег и клинических данных, и это записано в самом коде:
  routes/billing.ts:371  «Оплата любой клиники записывалась в ПЕРВУЮ организацию таблицы: деньги попадали
                          в чужую кассу, а у своей клиники не появлялись вовсе»;
  routes/clinical.ts:57  «Клиника Б проверяла противопоказания по НАБОРУ ПРАВИЛ КЛИНИКИ А»;
  routes/ai.ts:90, :104, :157 — то же.
Здесь он остался живым потому, что маршрут проверял ПРАВО на изменение (requireClinicalMutationAccess) и не
проверял ГРАНИЦУ АРЕНДАТОРА. Это две разные проверки, и наличие первой маскировало отсутствие второй —
ровно поэтому перепись маршрутов и не считала requireClinical* признаком исправности.

СТАЛО: requireResolvedOrganizationId — тот же охранник, что в починенном billing.ts. Организация приходит
из проверенного токена либо ответ 401. Второго способа выводить арендатора в проекте быть не должно.

СОЗНАТЕЛЬНО НЕ ВЗЯТ requireResolvedStaffOrAdminOrganizationId, хотя обработчик пишет actorUserId: он
дополнительно требует входа СОТРУДНИКА, то есть меняет доступ ШИРЕ самого дефекта. Ужесточение доступа —
отдельное решение, и делать его заодно с починкой границы арендатора нельзя.
Ответ 500 NoOrganizationFound снят не по недосмотру: организации «не найтись» больше не может, охранник
отвечает 401 раньше.

ДОКАЗАНО ЖИВЫМ СЕРВЕРОМ 127.0.0.1:4100, контрольные запросы ведущего, тела ответов приведены дословно.
Правило кампании соблюдено: «маршрута нет» и «нет доступа» различены по телу, а не по коду.

  A  валидное тело, БЕЗ КЛЮЧЕЙ           было 404 {"error":"CommunicationTaskNotFound","reason":"task_not_found"}
                                          стало 401 {"error":"AuthRequired","message":"Требуется авторизация…"}
  B  то же + x-organization-id ЧУЖОЙ      было 404 (заголовок не менял ничего)
                                          стало 401 — арендатор из клиентских данных не выдаётся
  E  контроль DELETE /api/clinical/rules       401 {"error":"AuthRequired",…} — идиома общего охранника

ЧТО ИМЕННО ДОКАЗЫВАЕТ ПЕРЕХОД 404 → 401. Прежняя 404 бросалась из communications.ts уже ВНУТРИ
db.transaction, ПОСЛЕ tx.select() — то есть обработчик исполнялся, организация была найдена и база была
опрошена для запроса без единого ключа. Теперь запрос отбивается охранником ДО базы, и ответ совпал с
контрольным маршрутом, у которого идиома была верной изначально. Две идиомы сошлись.

npm run typecheck -w @dental/api — истинный код выхода 0, снят без конвейера.
