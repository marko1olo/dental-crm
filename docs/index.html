Connected, not generic

The clinical day has more than one screen.

DENTE is shaped around the handoffs where a clinic loses context: from schedule to chairside work, imaging to documentation, and a completed visit to the next accountable action.

01 / Operations

Schedule and patient context

Appointment handling and patient profiles are designed to keep the relevant record close to the day’s work.

02 / Clinical

Visit-focused documentation

Clinical forms, treatment context, and visit workflows make the care record an active working surface rather than an archive.

03 / Imaging

DICOM workbench boundary

Study intake and imaging review tooling belong in the workflow while advanced interpretation stays with qualified clinical judgement.

04 / Documents

Controlled document lifecycle

Documents, issue states, and patient-facing forms are treated as a lifecycle with clear checks, not loose files.

05 / Finance

Payment and balance context

Financial information is part of the patient journey, with route-level guards around payment capture and related records.

06 / Follow-up

Scoped communications

Communication tasks and Telegram-oriented integrations are designed around explicit scope and visible follow-up outcomes.

Before the chair

At the chair

Give the visit a focused working surface.

DENTE concentrates the visit around patient context, clinical workflow forms, and the supporting tools needed during care rather than forcing a separate trail for every action.

  • Visit workflow and active-status controls
  • Clinical rules and mutation guards
  • Voice-to-note and review-oriented states

Evidence in context

Keep imaging and documents connected to the care record.

The codebase includes DICOM intake and workbench-oriented paths alongside document generation and lifecycle guards, making supporting evidence part of the traceable workflow.

  • DICOM file intake and imaging workbench boundaries
  • Document issue, preview, and lifecycle checks
  • Explicit source and payload validation routes

After the visit

Make the next action visible and owned.

Payments, communication tasks, and follow-up paths are represented as connected operational work so a completed encounter can lead to a clear next responsibility.

  • Payment capture and balance-related routes
  • Communication-task outcomes
  • Telegram control and handoff boundaries

Inspectable by design

A web application stack, visible in the source.

The repository is a TypeScript workspace. Its web client, Fastify API, shared package, and source-level smoke checks are separated so the product surface remains inspectable as it evolves.

Scope boundary DENTE is presented here as an evolving prototype. Repository documentation and source checks can demonstrate implementation intent; they do not constitute clinical, regulatory, security, or production-hosting certification.
Web clientReact 19, Vite, TypeScript, and a component-level interface layer.
APIFastify 5 with route-level middleware, validation, and WebSocket support.
DataDrizzle ORM and PostgreSQL, with the repository organized as a multi-package workspace.
ImagingCornerstone and DICOM-related packages for browser-side imaging workbench paths.
ChecksTypeScript compilation, encoding checks, source-level smoke scripts, and browser-oriented test tooling.

Read it honestly

Questions the page should answer directly.

The public surface deliberately distinguishes the codebase’s intended product direction from claims that would require real deployment, clinical, or regulatory proof.

Is DENTE a finished hosted service?

No. It is an active prototype repository. This page exists to describe the public codebase and its product direction without representing it as a generally available clinical platform.

What does the imaging workbench claim?

The repository contains DICOM-related intake and browser imaging dependencies. Imaging review is a workflow capability under development; diagnostic interpretation remains a clinical responsibility, not a claim made by this page.

Where can I verify the product surface?

Start with the repository README and source tree. The project keeps web, API, and shared packages separate, while scripts expose type checks and focused smoke checks for many product routes.
