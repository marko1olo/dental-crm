# Миграции базы данных

## Как применять

```bash
npm run db:migrate
```

Запускает `apps/api/src/scripts/migrate.ts`: применяет `drizzle/*.sql` по
возрастанию номера, каждый файл в отдельной транзакции, и отмечает применённые
в таблице `_dente_migrations`. Повторный запуск ничего не переприменяет.

| команда | что делает |
|---|---|
| `npm run db:migrate` | применить недостающие миграции |
| `npm run db:migrate:check` | показать, что будет применено, ничего не выполняя |
| `npm run db:migrate:baseline` | отметить все файлы применёнными, ничего не выполняя |
| `npm run db:migrate:strict` | то же, что `db:migrate`, но изменение уже применённого файла — ошибка (EXIT=1) |

`db:migrate:check` выполняет ТЕ ЖЕ проверки файлов, что и боевой прогон, и падает
на том же файле. Разница между режимами только в том, применяются ли изменения.

> `npm run db:migrate -- --strict` из корня репозитория **не работает**: npm
> отдаёт `--strict` внутреннему `npm run` как свою опцию, и до скрипта флаг не
> доходит — прогон завершается с EXIT=0 при разошедшейся контрольной сумме.
> Пользуйтесь `npm run db:migrate:strict`.

`--baseline` нужен ровно один раз и только для базы, которая **уже наполнена**.
До появления раннера схему досоздавали 52 модуля выражениями
`CREATE TABLE IF NOT EXISTS` прямо во время обработки запросов, поэтому в
существующей базе часть таблиц есть, а таблицы учёта — нет. Без `--baseline`
первый же `CREATE TYPE` из `0000` упал бы на «already exists».

Порядок для действующей установки:

```bash
npm run db:migrate:baseline
```

затем добавлять новые миграции обычным `npm run db:migrate`. Для чистой базы
`--baseline` не нужен.

## Конфигурация drizzle-kit

`apps/api/drizzle.config.ts` использует `dialect: "postgresql"` с подключением через `DATABASE_URL` из корневого `.env` (PostgreSQL 18.4 на `127.0.0.1:5432`). PGlite полностью удалён из проекта.

**Миграции выполняются каноническим раннером:**
```bash
npm run db:migrate
```
Раннер `apps/api/src/scripts/migrate.ts` применяет SQL-файлы из этой папки и фиксирует их в таблице `_dente_migrations` в рабочей базе PostgreSQL.

**`meta/_journal.json`:** Учёт применённых миграций ведётся в самой базе в таблице `_dente_migrations`. Все новые миграции нумеруются по возрастанию (`NNNN_короткое_описание.sql`).

## Правила

- Имя файла: `NNNN_короткое_описание.sql`, номер по возрастанию, четыре цифры.
- Применённый файл не редактируют: раннер сверяет sha256 и предупреждает о
  правке. Изменение уже применённой миграции не догоняет базу — заводите новый
  файл.
- Миграция с `CREATE INDEX CONCURRENTLY` обязана начинаться строкой
  `-- no-transaction` (см. `0155`, `0156`). Postgres запрещает CONCURRENTLY
  внутри транзакционного блока, а несколько выражений в одном запросе он
  оборачивает в НЕЯВНУЮ транзакцию — поэтому такие файлы раннер выполняет по
  одному выражению за вызов, вне транзакции. Каждое выражение должно быть
  идемпотентным (`IF NOT EXISTS`): отката у такого файла нет.
  Слово CONCURRENTLY в комментарии маркера НЕ требует — раннер ищет его в
  исполняемом тексте, а не в комментариях.
- Новая таблица заводится миграцией, а не выражением
  `CREATE TABLE IF NOT EXISTS` в обработчике запроса. Это проверяет
  `npm run smoke:schema-ddl-coverage`.
- Колонка, объявленная в `db/schema.ts`, должна существовать в DDL: drizzle
  подставляет её имя в каждый запрос, и её отсутствие роняет все обращения к
  таблице целиком. Это проверяет `npm run smoke:schema-column-parity`.
